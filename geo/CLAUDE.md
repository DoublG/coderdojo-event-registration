### Geo search: MySQL spherical distance

`django.contrib.gis`'s `Distance()` only gets proper spherical/spheroidal math substituted on PostGIS — on MySQL it silently returns a raw planar-degree value. `geo/functions.py` defines `DistanceSphere`, a `GeoFunc` subclass wrapping MySQL's `ST_Distance_Sphere`, so the real distance is still computed in the database rather than in Python. **Always use `geo.functions.DistanceSphere` for any new distance-based query against `PointField`s — never Django's built-in `Distance()`, and never compute distance in Python.** See `dojos/search.py` (`dojos_by_distance`) for the reference usage: annotate with `DistanceSphere(F("location"), origin) / 1000.0` and order by it.

The dojo-finder search (`dojos/search.py`) resolves an "origin" point with a fixed priority: typed address (geocoded via `geo.geocoding.geocode`, a thin Nominatim/OpenStreetMap client restricted to Belgium) > browser-supplied lat/lon ("use my location") > the logged-in account's postcode (`User.postal_code`, optional; `dojos.search.postal_code_origin` averages that postcode's `geo.Municipality` centres) > a hardcoded Ghent default. Only the Ghent default is cached (`dojos_by_distance` checks the origin's identity), so one family's list never leaks to another visitor. It's shared by both the full dojo-finder page and the homepage's embedded widget — `pages.views.home` calls the same `resolve_search_origin`/`dojos_by_distance` helpers. **The events list's Location filter** (`events.search.filter_by_place`) geocodes the place the same way and keeps the sessions within `NEAR_RADIUS_KM` (20) of where each is held, `events.search.where_held()`: `Event.location` when set, else the dojo's (`Coalesce`); when the place can't be found it falls back to matching the text (dojo address, municipality, venue).

**Nominatim allows one request a second for the whole site, so `geo.geocoding.geocode` is the only way to call it** (never `requests` directly): it answers from the cache first (by the normalised text, hashed so what was typed isn't stored; a match 90 days, a no-match a day), then from `geo.Municipality` for a postcode or a municipality's name, and only then asks Nominatim, after taking the site-wide slot in Redis (`SLOT_KEY`, 1.1 s; a page waits at most `WEB_WAIT_SECONDS`, a command passes `wait=None`). A 429/503/403 from Nominatim stops every call for a while (`BACKOFF_KEY`), and without Redis it never calls. Not getting a slot raises `GeocodingUnavailable` (a `requests.RequestException`, so callers treat it as a failed lookup, never cached). `/metrics/` counts `geo:geocode` (the cache) and `geo:local-lookup` (its misses are the Nominatim requests).

**Map widgets: two, one library.** `geo.widgets.BelgiumOSMWidget` is the Django admin's (a fork of Django's `OLMapWidget.js` in `geo/js/belgium_map_widget.js`, any geometry, the province overlay); `geo.widgets.PointPickerWidget` is for the site's own forms (the event form's *Place on the map*, `Event.location`): one pin, its own template (`geo/widgets/point_picker.html`) and script (`geo/js/point_picker.js`), keyboard buttons (pin in the middle of the map, remove it), texts from the catalogs and the form (`reference`, `reference_label`, `reference_empty_text`: geo knows no dojo), no province overlay (230 KB on every page). Both stand on Django's GIS form field and widget base (GeoJSON in the hidden input; the picker keeps it in longitude/latitude, `map_srid` 4326), the vendored OpenLayers and the OpenStreetMap tiles the CSP allows. A page using the picker renders `{{ form.media.css }}`/`{{ form.media.js }}` (the dojo admin's `admin_extra_style`/`admin_extra_script`). The picker writes the input only after the user moves the pin, so a save without touching the map isn't a change.
