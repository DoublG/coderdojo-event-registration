We pushed the live hosting past what it can take, on purpose. At this size the nightly work first got stuck at the hosting's memory limit. It now works in small batches, so its memory stays the same however large the organisation grows.

Tested on 8 October 2026 on the live hosting, switched for the test to a throwaway copy of the data at the size of the "stretch" scenario after five years: 150 dojos, 43,298 children, 410,400 bookings. The nightly engagement rebuild (how each child comes to sessions, used by the dashboards and by mail journeys) then took the background workers to the hosting's memory ceiling of about 512 MB, where the server slows every process down instead of stopping one: mail stood still and after 19 minutes the job failed. The same day the rebuild was changed to work 500 children at a time, each batch with its own database connection, and a stuck run is no longer retried. Retested on the same data: 101,049 rows in 36 seconds, the worker flat at 181 MB, all background work together at about 383 MB, mail going out as usual. With today's real data it takes a quarter of a second. And should something ever run away anyway: the hosting now stops it at the memory limit within 20 seconds, the background work is back 10 seconds later, and the mail dispatcher keeps running throughout (tested on 8 October 2026).
