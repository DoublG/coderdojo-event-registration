# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Multiple AI agents/sessions may work in this repo. Keep this file authoritative and current: if you change something it describes (settings, workflows, conventions), update the relevant section in the same change rather than leaving it stale for the next agent.

## What this is

A Django site for CoderDojo Belgium: dojo discovery/search, event registration, self-service family accounts, account-level applications (champion / mentor) with a Belgian legal background-check workflow, dojo teams and their admin area, learning pathways, ninjas' badges and belts, and organisation roles for the management side (the Django admin). No separate frontend build — server-rendered Django templates plus [htmx](https://htmx.org/) for the dynamic bits (see Architecture below), a hand-maintained `core/static/core/{js,css}/bundle.{js,css}` (no bundler/npm in this repo), and vanilla CSS/HTML for anything that doesn't need a server round-trip.

## Workflow rules

- **Always work inside the `.devcontainer`, never against the host Python/MySQL.** Before running `manage.py` commands (migrations, `runserver`, and especially `manage.py test`), check the stack is actually up — `docker ps` should show `coolregistration-dev-workspace`/`-db`/`-redis`/`-proxy` as `Up`; if it isn't, start it (`docker compose -f .devcontainer/docker-compose.yml up -d`) rather than falling back to a host-level run. Run commands via `docker compose -f .devcontainer/docker-compose.yml exec workspace <command>` (or `exec workspace bash` for a shell). This matters beyond convention: the notification bell's WebSocket support (Django Channels, see Architecture) depends on Redis and on `daphne` actually serving `runserver`'s ASGI app, both of which the devcontainer wires up for you — a host run can silently diverge (e.g. a stray host MySQL, or no Redis at all) without it being obvious from the command output alone.
  - **One exception: testing nginx's own behavior, or any real end-to-end check, has to go through the host.** `docker compose exec workspace` talks to Django directly and never touches the `proxy` container at all — TLS termination, the `/docs/` and `/mails/` (Mailpit) aliases, and (since adding WebSockets) the `Upgrade`/`Connection` proxy headers all live in nginx, not Django, so a workspace-only check can pass while the thing a real client actually hits is still broken. Verify those from the host against the real FQDN (`https://coolregistration.localhost`, `wss://coolregistration.localhost/ws/...`) — plain `127.0.0.1`/internal-port requests skip nginx *and* fail `ALLOWED_HOSTS`/origin checks that key off `coolregistration.localhost`. A hand-written test client also needs to send an `Origin` header matching that FQDN (a real browser always does this automatically) or Channels' `AllowedHostsOriginValidator` (see Architecture) rejects the connection with a 403 that has nothing to do with the thing you're actually testing.
  - **Editing `.devcontainer/nginx/nginx.conf` needs a proxy recreate, not just a save.** It's a single-file bind mount (`docker-compose.yml`), which Docker pins to the file's *inode* — the same gotcha `docs/README.md` already documents for `docs/build/`. An editor/tool that replaces the file (rather than writing in place) leaves the running `proxy` container looking at the old, deleted inode forever; `nginx -s reload` inside it changes nothing because it's reloading that same stale content. Fix: `docker compose -f .devcontainer/docker-compose.yml up -d --force-recreate --no-deps proxy` (the `--no-deps` matters here too, same reason as `docs/README.md`'s note).
- **Non-technical work belongs in the management dashboards; the Django admin is the always-working emergency tool.**
  - **Day-to-day work goes in a dashboard.** Anything the organisation or a dojo team does as part of their normal work (running campaigns, building segments, managing events, teams, content, ...) gets a page in the matching management dashboard, to keep it user-friendly and consistent with what's already there: the dojo area (`/dojos/<id>/…`, `dojos/_admin_base.html`) for a dojo's team, the organisation area (`/manage/…`, `core/_manage_base.html`) for the organisation. Build it the same way as the existing pages: same shell and sidebar, `cd-*` styling, server-rendered forms plus htmx, access through a helper (`dojos.access`, `accounts.organisation`), 404 for anyone without access.
  - **The Django admin (`/admin/`) is for technical interventions**, and for features that don't have a dashboard page *yet*: inspecting or fixing data, the mail log, bounces and suppressions, periodic tasks.
  - **The admin always stays fully usable.** Whatever breaks, it must be fixable there, so that direct database access is never needed. Never make a model read-only in the admin, never hide its fields, and never override `has_add/change/delete_permission` to block things. Let Django's permissions decide: a superuser can always do everything, and a role gets what its group grants (`accounts.organisation`). That holds even for append-only logs and rule-enforced data (belt history, the consent log, background-check decisions): say in the ModelAdmin's docstring that an edit there bypasses the normal rules, and don't block it. A feature that gets a dashboard page keeps its full admin page too. `core.tests.AdminStaysFullyUsableTests` checks that a superuser can add, change and delete every registered model; a genuine exception needs its reason in that test's `EXCEPTIONS`.
- **New features need tests.** Any new view/route, model behavior, or non-trivial function added to this repo should come with a corresponding test in the relevant app's `tests.py` (see `accounts/tests.py`, `dojos/tests.py`, etc. for the established route-test style: status codes, template used, auth/permission gating, and the actual DB effect of a POST). Don't leave a new feature untested on the assumption someone will backfill it later.
- **Keep the end-user docs current.** `docs/` (Sphinx, built with `make html-all` from inside `docs/` — en/fr/nl, see `docs/README.md`; deps in `docs/requirements.txt`) is the help-centre content for families/volunteers/dojo teams — not this file. If a change alters a user-facing flow this documents, update the relevant `docs/source/**/*.rst` page **and** its French/Dutch translations (`docs/source/locale/{fr,nl}/LC_MESSAGES/`, see `docs/README.md` for the extract/update workflow) in the same change. It intentionally only documents flows that are actually wired up end-to-end.

## Commands

Run everything inside `.devcontainer/` (nginx + TLS on `coolregistration.localhost`, containerized MySQL, Redis, Mailpit, two Celery workers with beat embedded in one) — see the workflow rule above. `website/settings.py` reads `DB_*`/`REDIS_*`/`EMAIL_*`/`COOKIE_DOMAIN` env vars with host-friendly defaults (so a host-level run isn't *broken*, just not what this repo's workflow expects — Redis/Channels behavior in particular can diverge, see above); `.devcontainer/docker-compose.yml` sets the real ones.

```sh
docker compose -f .devcontainer/docker-compose.yml up -d          # db, redis, proxy, workspace — check first with `docker ps`
docker compose -f .devcontainer/docker-compose.yml exec workspace bash    # a shell inside the workspace container
```

From that shell (or prefix any of these with `docker compose -f .devcontainer/docker-compose.yml exec workspace`):

```sh
# Dev server — reachable via https://coolregistration.localhost through nginx
python manage.py runserver 0.0.0.0:8000

# Migrations
python manage.py makemigrations <app>
python manage.py migrate

# Tests (plain Django test runner — no pytest config in this repo)
python manage.py test                    # all apps
python manage.py test accounts           # one app
python manage.py test accounts.tests.SomeTestCase.test_something   # one test
# If the debug toolbar's E001 check refuses to run tests, add --debug-mode
# (keeps DEBUG=True for the run) rather than working around it in settings.
python manage.py test --debug-mode

# Django shell / admin superuser
python manage.py shell
python manage.py createsuperuser

# Translations (LANGUAGES in settings.py: en-us, nl-be, fr-be, de — switching
# mechanism is wired up per-request/session, but no .po catalogs exist yet)
python manage.py makemessages -l nl_BE
python manage.py compilemessages
```

Claude Code's login/settings/session history in the `workspace` container live on the `claude-config` named volume (mounted at `/root/.claude`, with `CLAUDE_CONFIG_DIR` pointing there so `.claude.json` is inside it too) — a rebuild keeps them; only `docker compose ... down -v` wipes them (along with the DB volume).

Regenerating the local dev TLS CA/cert for `coolregistration.localhost`: see `.devcontainer/certs/README.md`.

**Requirements are split:** `requirements.txt` holds only the **production runtime** dependencies (what the running site imports, plus their pinned transitive deps; `scripts/deploy.sh` installs this on the server). `requirements-dev.txt` includes it via `-r` and adds ruff, the data-loading stack used only by the `import_*` commands (`geopandas`, `pandas`, `shapely`, `bs4`, ...; imported *inside* those commands, never at module level). The devcontainer image installs `requirements-dev.txt`. A new package the site imports at runtime goes in `requirements.txt`; anything only needed locally goes in `requirements-dev.txt`.

Lint/format — `ruff` (config in `pyproject.toml`; tool itself in `requirements-dev.txt`, not `requirements.txt`):

```sh
pip install -r requirements-dev.txt
ruff check .              # lint
ruff format .             # format
```

### Deploying (Level27)

Production is Level27 Python hosting, reached over SSH with key auth (`py10102@c40a7b15f.l27powered.eu`). `scripts/deploy.sh --check` is a read-only preflight; `scripts/deploy.sh` does the real deploy. It bundles the working tree (dev-only paths excluded), installs `requirements.txt` into the **pyenv env gunicorn runs from** (`~/.pyenv/versions/py10102-3.14.7`, *not* `~/app/.venv`), runs `manage.py check` on the new code *before* touching the live app, rsyncs into `~/app` (keeping `.env`, `media/`, `private_media/`), migrates, then reloads gunicorn (HUP to its master) and smoke-tests over the unix socket. Level27 runs `gunicorn -k uvicorn.workers.UvicornWorker main:app` from `~/app`; that command is managed on their side, so the repo-root `main.py` just re-exports `website.asgi.application` as `app`. Production env vars live in `~/app/.env` on the server. To replace it, put a local `.env.production` (gitignored via `.env.*`) next to the script and it gets uploaded. **Celery workers:** every deploy installs the two systemd *user* units from `scripts/systemd/` (uploaded separately, since `scripts/` isn't bundled), restarts them so they run the new code, and pings them; `--check` shows their state. All mail goes through them, so a deploy that can't start them (no Redis, or no systemd lingering for `py10102`) fails loudly after the site is live. The server has **no MySQL client headers and no GDAL/GEOS**, so `mysqlclient` and `django.contrib.gis` can't work there until that's solved; the script's `manage.py check` step stops a deploy before it can break the live site.

No CI (`.github/workflows` doesn't exist) — these run locally only, on demand.

The devcontainer's `db` service auto-grants its app user rights on Django's `test_<DB_NAME>` database via `.devcontainer/db-init/01-grant-test-db.sql` (runs once, on a fresh volume, via MySQL's `docker-entrypoint-initdb.d`), so `manage.py test` works there with no setup. Outside the devcontainer (a plain host-based MySQL), Django's test runner needs `CREATE`/`DROP DATABASE` on `test_<DB_NAME>`, which a DB user only ever granted rights on its own named database won't have — grant it once: `GRANT ALL PRIVILEGES ON \`test_<DB_NAME>\`.* TO '<DB_USER>'@'%';`.

## Architecture

### Apps and what owns what

Mermaid diagrams of the whole data model (entities, role/access rules, event and background-check state machines) live in `DATA_MODEL.md` — update the relevant diagram when you change a model or one of those flows. **The data-model redesign has landed** (all eight phases; `DATA_MODEL.md` §10 keeps its rationale, implementation decisions and plan; e.g. one `User` table with `account_type` instead of role subclasses; which also fixes the **nomenclature**: **Champion** = the dojo owner, **Mentor/Coach** = an adult helper, **Ninja** = a child aged 7–17 visiting a dojo, **Youth mentor** = a ninja helping run events, **Badge** = an award, one-off or a count-based milestone such as the attendance wristbands, **Belt** = a ninja's proficiency level, separate from milestones (a milestone badge can optionally grant a belt), stored as an append-only belt history (current level = the highest belt, `Ninja.current_belt`; it's the only record of a ninja's coding level — there's no separate experience-level field), shown on the ninja's account page, the family page's child cards and in the management tooling (attendance rows, the ninja admin list), awarded only by accounts that actively manage a dojo (an active champion/mentor membership, recorded along with the account; organisation accounts can only view belts), and not linked to pathways yet). Use these names in code and UI. The model:
- **Accounts:** two account types, a normal account (background-checked only to become a champion or mentor) and a ninja account. Champion, mentor and youth mentor are roles on a User↔Dojo membership, replacing the `Mentor` table and the `DojoOwner`/`HelperAccount`/`Guardian` subclasses.
- **Joining:** mentor/champion approval is one-time and account-level. Joining a dojo is then a request the dojo's team accepts (or they add you). Memberships go `requested → active → dormant`, with dormant ones kept for past event teams.
- **Dojo lifecycle:** `draft → active ⇄ dormant → archived → draft`. The champion launches without approval. Dormant and archived both require no active events and auto-decline pending join requests. Dormancy is always manual, prompted after six months with no events by a dashboard flag and a persistent team/board notification. Hidden dojos stay in ninjas' history.
- **Champion role:** moves only by transfer to an active mentor. Any active mentor can accept join requests, add mentors and promote youth mentors.
- **Profiles:** the team-page profile is on the account, shared across dojos. `ORGANISATION_TEAM_MEMBER` is a display-only listing with a position (e.g. "Member of the board"), separate from management-dashboard access (`ORGANISATION_ROLE`).
- **Pathways:** optional many-to-many links at dojo → event → registration, each pre-filled from the level above.
- **No data migration:** the database only holds seeded test data, so the redesign's migrations were reset to a fresh initial set per app (an older dev database has to be recreated — see `DATA_MODEL.md` §10 "No data migration", including how to reset only the database without `down -v` wiping the `claude-config` volume). Seeders: `seed_champions`, `seed_mentors`, `seed_guardians`, `seed_events`, `seed_applications`, `seed_ninja_history`, `seed_faqs`, `seed_testimonials`, `seed_announcements` (random updates for dojos that have none; order in `.devcontainer/start.sh`), `seed_organisation` (the organisation dojo, its two events and a promotion per placement), and `seed_mailing` (example email templates and draft campaigns; no dates, so `start.sh` runs it on every start); keep them rerun-safe — a choice made only when a row is new must use its own RNG, not the command's shared one.
**Organisation-run events** (CoderDojo Girlz, Coolest Projects) live on an **organisation dojo** (`Dojo.kind = organisation`, `DATA_MODEL.md` §12): a normal dojo with a team, admin area and background-check rule, but never listed (`Dojo.objects.public()`/`is_public` exclude it; its event pages say "Organised by", `events/partials/_organiser.html`). Only its events can set `Event.external_registration_url` (the page links out, `event_signup` redirects, no registrations here). New code that lists or picks dojos should go through `public()`, or exclude `kind=organisation` explicitly. **Promoting events** is `content.Promotion` (an event, a `placement` of four, `rank`, a `starts_at`/`ends_at` window): always read it through `Promotion.objects.showing(placement)`, managed on the organisation dashboard (`/manage/promotions/`, `content/manage.py`).
Keep routing role checks through `dojos.access`, team changes through `dojos.team`, onboarding through `applications.services` and badges/belts through `events.awards`.

- **`accounts`** — the `User` model and everything auth-related.
- **`dojos`** — `Dojo` (with its lifecycle status), `DojoMembership` (dojo teams; rules in `dojos/team.py`, access in `dojos/access.py`), geo-search.
- **`events`** — `Event`, `Registration` (and the `RegistrationCancellation` log), badges and belts (`Badge` one-off/milestone, `NinjaBadge`, `Belt`, the append-only `NinjaBelt` history; rules in `events/awards.py`), the session team's attendance (`TeamAttendance`), and the nightly engagement snapshot (`NinjaEngagement`, `NinjaEngagementChange`; `events/engagement.py`, `events/tasks.py`).
- **`applications`** — the account-level onboarding: `Application` (mentor / champion), the background-check flow on the account and its `BackgroundCheckHistory` audit log (`applications/services.py`), and the reviewers' admin.
- **`pathways`** — the learning-track catalog (`Pathway`, `PathwayStep`, `PathwayProject`, `Skill`); read-mostly, no user-facing enrollment state. Linked (redesign phase 4) at three optional M2M levels, each pre-filled from the one above but never restricted to it: `Dojo.pathways` (Settings page) → `Event.pathways` (`EventForm` pre-selects the dojo's on a new event) → `Registration.pathways` (copied from the event at `event_signup`, narrowed per row on the attendance list via `dojo_event_registration_pathways`).
- **`content`** — `FAQ`, `Testimonial`, `Announcement`, each optionally scoped to a Dojo/Event/Pathway or global when the scoping FK(s) are blank; `Promotion` (featured events, see above) and its organisation-dashboard page (`content/manage.py`, `content/urls.py`).
- **`notifications`** — a minimal per-user `Notification` model (no views/urls of its own — read directly by whatever renders it).
- **`mailing`** — every mail the site sends (the `send()` gateway, the queue in `EmailMessage`, the Celery tasks in `mailing/tasks.py`, bounces), mail preferences and consent, and the organisation's campaigns, journeys, segments and mail templates (the organisation dashboard, `mailing/manage.py`). See "Background jobs" and "Mailing and segmentation" below.
- **`geo`** — `AdministrativeBoundary` / `Municipality` reference data, the Nominatim geocoding client, and the custom `DistanceSphere` GIS function (see below). No urls.py.
- **`core`** — the homepage view (composes widgets from `dojos`/`events`/`pathways`/`content`) and shared templates/static (`core/templates/core/menu.html` nav, the organisation dashboard's shell `core/_manage_base.html`, the `get_item` template filter, `bundle.js`/`bundle.css`).
- **`website`** — settings/urls/asgi, the Celery app (`website/celery.py`), and a stub external API (`website/api.py`, django-ninja, work in progress: for events whose registration or attendance is handled by an outside app).

Each app with URLs owns its own `urls.py`, included from `website/urls.py` with an empty prefix (`path("", include("dojos.urls"))` etc.) — routes live at the top level, not namespaced under `/dojos/`, `/events/`, etc.

### Account model

`accounts.User` (`AUTH_USER_MODEL`) is every login; `User.account_type` is `adult` or `ninja` (a ninja's own login — `user.is_ninja`). **Parents aren't a role or subclass any more** (redesign phase 1, `DATA_MODEL.md` §10): any adult account is linked to its children through `accounts.Guardianship` (a child can have several guardians), and `Ninja.objects.of_guardian(user)` is how to get "this account's children" — never filter on a guardian FK on `Ninja` (there isn't one). Family pages live under `/account/` with no id in the URL (`account_home`, `ninja_detail`, `edit_ninja`, `ninja_badges`, `add_ninja`, `ninja_login_create`/`_resend`/`_remove`, `cancel_registration`), always scoped to `request.user`; `accounts.views._get_own_ninja` 404s (not 403s) for a ninja the account isn't a guardian of, and with `allow_self=True` also lets a ninja's own login view (never edit) its own page.

There are **no role subclasses of `User` any more**: being a champion or mentor is an approved `applications.Application` plus a valid background check on the account (redesign phase 3), and what they do at a dojo is a membership (below). `accounts.context_processors.user_roles` exposes `user_is_approved_champion` / `user_is_approved_mentor` / `user_applied_champion` / `user_applied_mentor` / `user_admin_dojo` / `user_has_organisation_role` to every template. There's no multi-table inheritance left anywhere: badges are one `events.Badge` table with a `kind` (`one_off` / `milestone`).

`accounts.Ninja` (a child aged 7–17; formerly `Participant`) is a plain model, *not* a User — a ninja only gets a login (a `User` with `account_type="ninja"`, linked via `Ninja.account`) if a parent opts them in; most don't have one. Registrations, badges and belts link to it as `ninja`. **A ninja's own login is the guardian's to give and take away** (`DATA_MODEL.md` §17): always through `accounts/child_accounts.py` (`give_login` with the child's own email → a ninja `User` with no usable password plus the `ninja_account_created` set-password mail; `remove_login` deletes it, or disables it (`is_active=False`) and ends its memberships when it was ever on a dojo team, since `Event.team` points at memberships). The guardian keeps editing the child's details either way. A ninja's login signs itself up for sessions and cancels its own places: event sign-up lists `Ninja.objects.signable_by(user)` (an adult's children, or the ninja itself), never `of_guardian` directly. **A ninja's home dojo** (`Ninja.home_dojo`, `member_since`) follows `accounts/home_dojo.py` (`DATA_MODEL.md` §18): set at the child's first sign-up from that session's dojo (never an organisation dojo), then only the guardian changes it (child edit form); never moved automatically, never by the dojo team. The 7–17 rule (`accounts.models.ninja_birth_date_error`) applies whenever a date of birth is entered or changed — `Ninja.clean()` and the family forms check it; it's never retroactive, so a ninja who has turned 18 stays editable.

**Dojo teams are memberships** (redesign phase 2): `dojos.DojoMembership` is one account's place on one dojo's team — `role` (`champion` = the dojo's owner, exactly one active per dojo; `mentor`; `youth_mentor` = a ninja account, `promoted_by` a champion/mentor of the same dojo) and `status` (`requested` → `active` → `dormant`, unique per account+dojo; leaving goes `dormant`, never deleted, so `Event.team` keeps its history, and rejoining reuses the row). There is no `Dojo.owner` and no `Mentor` table any more — `dojo.champion` / `dojo.champion_membership` give the owner, `dojo.memberships.managers()` the active champion+mentors, `for_team_page()` the public listing (champion first). The team-page profile (`display_name`/`title`/`bio`/`photo`/`show_on_team_pages`, `user.team_name`) lives on `accounts.User` and is shared by every dojo the person is on; `DojoMembership` exposes it (`.name`, `.photo`, ...) so the shared `_mentor_avatar.html` partial works for memberships and `content.OrganisationTeamMember` (the organisation's display-only team listing, with a `position`) alike. **Every team/lifecycle change goes through `dojos/team.py`** (`request_to_join`, `accept_request`, `add_mentor`, `promote_youth_mentor`, `leave`, `transfer_champion`, `change_status`, `notify_managers`, ...), which enforces the rules and raises `TeamError` with a user-facing message — don't edit memberships or `Dojo.status` directly from views. `Dojo.status` is `draft` (model default) → `active` ⇄ `dormant` → `archived` → `draft`; only `active` dojos are public (`Dojo.objects.public()`, and `Event.objects.visible()` also requires `dojo__status=active`); going dormant/archived needs no upcoming draft/open events and auto-declines pending requests; `change_status` also clears the dojo finder's cached default list. Tests: use `dojos.testing.make_dojo(name, champion=..., status=ACTIVE)` / `add_member(...)` rather than `Dojo.objects.create` (which gives a hidden draft).

**Organisation roles** (redesign phase 6): `accounts.OrganisationRole` (`board` = read-only oversight + the organisation's team listing, `admin` = also edits dojos/events/content/catalogues and runs mail campaigns) is access to the management side: the organisation dashboard (`/manage/`, admin role only, `accounts.organisation.is_organisation_admin` / `require_organisation_admin`) for what has a page there, and the Django admin for everything else and for emergencies. `accounts/organisation.py` maps each role to a permission group and syncs `is_staff` + groups via signals — grant/revoke the role, never set those by hand. Neither role can award belts or review background checks. Admin actions that change data should declare `permissions=["change"]`, or view-only roles can run them.

Every account is created by its own holder (family sign-up) — there are no admin-provisioned logins or emailed temporary passwords any more. `accounts.middleware.ForcePasswordChangeMiddleware` still redirects any account with `must_change_password` set (e.g. by an admin after a reset) to the password-change form. `accounts.backends.EmailOrUsernameBackend` lets login accept either email or username.

Family sign-up is self-service (`accounts.views.register_guardian`, `RegisterGuardianForm`; a logged-in account is redirected to its account page instead) — no admin approval or background check, since a parent only ever manages their own children (unlike champions and mentors, who work directly with other people's kids and need the background check). It creates a plain adult `User` plus a `Guardianship` per child; the username comes from `accounts.provisioning.unique_username()`. The child rows on that form are dynamically numbered by JS (`child_<n>_name` etc., possibly non-contiguous after a "Remove") rather than a Django formset — see `accounts.views._parse_child_rows`.

### Applications → background check → approval (account-level)

Onboarding is **per account, not per dojo** (redesign phase 3, `DATA_MODEL.md` §6). All of it lives in `applications/services.py`; views and admin actions only call it (`OnboardingError` carries a user-facing message).

1. A logged-in **adult** account applies (`register_dojo` → `Application.CHAMPION`, `register_helper` → `Application.MENTOR`; one pending/approved application per account and kind). Anonymous visitors are sent to log in first — accounts always exist before applying. A mentor application naming a dojo notifies that dojo's managers.
2. A reviewer requests the **account's** background check (`request_background_check`: sets `User.background_check_status=requested`, creates `background_check_token` if missing, emails the upload link). Re-running it on an account whose check isn't currently valid is how a renewal is requested.
3. The account holder uploads the document — via the emailed token link (`upload_background_check`, no login needed) or from their account page (`renew_background_check`). It's stored on `applications.storage.private_storage` (`base_url=None`, no public URL; model fields reference it through the `get_private_storage` callable so migrations don't embed the machine-specific path); the only read path is the permission-gated `download_background_check` view.
4. A reviewer with `applications.can_review_background_checks` validates or rejects it (the **Background checks** admin list, a proxy over `User`). **Either decision deletes the document immediately** and appends a `BackgroundCheckHistory` row (decision, reviewer, when, expiry) — an append-only audit log that nothing reads to decide access. Validation sets `background_check_expires_at` = now + `BACKGROUND_CHECK_VALIDITY` (365 days).
5. With a valid check, a reviewer approves the application (`approve_application`). An approved **mentor** can ask to join any dojo's team or be added (`is_approved_mentor`; an approval naming a dojo files the join request there); an approved **champion** can create dojos (`is_approved_champion`, `dojos.views.dojo_create` → a `draft` dojo with them as champion). An approved champion also counts as an approved mentor.

If you touch this flow, keep the "delete the document, keep only the decision" property — it's deliberate, not an oversight.

**A lapsed check never blocks login.** `User.background_check_valid` is "validated and not expired"; once false, the account's champion/mentor memberships stop granting dojo access (`dojos.access`) and it stops counting as approved, but the person can still log in and use the site (e.g. as a parent). The account page's Volunteering card links to the upload whenever `background_check_can_upload`. Parents and ninjas never need a check.

### Dojo admin area (champions and mentors)

A dojo's admin screens (`/dojos/<id>/dashboard/` = attendance, `/dojos/<id>/manage/` = profile settings, `/dojos/<id>/events/` = events list, `/dojos/<id>/events/new/` = create an event, `/dojos/<id>/events/<event_id>/` = edit an event, `/dojos/<id>/events/<event_id>/attendance/` = take attendance for that event, `/dojos/<id>/manage/team/` = the Team page, `/dojos/<id>/manage/updates/` = the Updates page (post/remove the "From this dojo" notes, `content.Announcement`, dated the day they're posted; the public page shows the newest `PUBLIC_UPDATES_LIMIT` = 5), `/dojos/<id>/manage/lifecycle/` = the champion's status actions, `/dojos/<id>/manage/members/` = the Members page (children whose home dojo it is, with a Promote-to-youth-mentor button)) all extend `dojos/templates/dojos/_admin_base.html`, which owns the whole `<!doctype html>` shell (it doesn't extend `core/base.html` — this is an app-like admin surface with its own collapsible-sidebar layout via `CoderDojo.initAdminNav`, not a scrollable marketing page). The page scrolls naturally (no inner fixed-height/`overflow` scroll container) — `.cd-admin-nav`'s height comes from the shell's default flex `align-items: stretch` matching `.admin-main`'s natural content height, so the sidebar's background/border always run the full length of the page, however long that page is. Sidebar markup matches the CoderDojo design system's `AdminNav`/`AdminDashboard` components. A page extending it fills `admin_page_title`/`admin_heading`/`admin_content` (and optionally `admin_topbar_extra`, `admin_extra_style`/`admin_extra_script`) and passes an `active` context var (`"attendance"`, `"settings"`, `"events"`, `"team"`, `"updates"`, ...) matching the sidebar link it should highlight. Every view here is `@login_required` and resolves its dojo through `dojos.access.require_dojo_access(request, dojo_id, capability)` — **never `get_object_or_404(Dojo, ...)` alone** for an admin view, or anyone can reach it by guessing an id — and renders with `dojos.views._admin_context(request, access)`.

**Who gets in, and what they can do** (`dojos/access.py`): an **active `champion` or `mentor` membership** at the dojo, held by an account whose background check is valid (`managing_membership`); youth mentors, requested and dormant memberships get nothing. No role → 404 (same reasoning as `accounts._get_own_ninja`); a role lacking the view's capability → 403. Capabilities: `TAKE_ATTENDANCE`, `MANAGE_EVENTS` (create/edit/status), `EDIT_SETTINGS` (`dojo_manage`), `MANAGE_TEAM` (Team page actions), `AWARD_BELTS` (phase 5), `POST_UPDATES` (the Updates page) and `MANAGE_LIFECYCLE` (launch/dormant/archive/reopen); the dashboard, events list, Team page view and notification endpoints need only *a* role, leaving needs any role, and handing over the champion role is champion-only (`access.is_champion`, never a capability). `ROLE_CAPABILITIES`: champion gets everything, **mentors everything except `MANAGE_LIFECYCLE`**; restricting mentors is just removing entries there. Who may *join* a team is `access.is_approved_mentor` (an approved mentor or champion `Application` plus a valid background check — `applications.services.is_approved_mentor`). Templates read `dojo_access.can_*` to hide what the viewer can't use and `dojo_access.role_label` (Champion/Mentor) for the sidebar; the dojo switcher lists `admin_dojos` (`accessible_dojos(user)`, including draft/dormant/archived dojos their team still manages). The same `accessible_dojos` drives the post-login redirect and the nav's "Manage" link (`user_admin_dojo`). A new admin view must pick its capability explicitly; if it's a genuinely new kind of action, add a capability rather than reusing a loosely related one.

`dojos.views.dojo_manage` (`DojoProfileForm`), the events screens below, attendance, the Team page, the lifecycle card, the Updates page, the Members page and the notification bell (below) are all wired to real data. The dashboard shows a banner for a non-active dojo, or the six-month dormancy nudge (`dojos.team.needs_dormancy_nudge`, computed per request). `dojo_manage` covers everything shown on `dojo_detail.html` (including the pathways the dojo provides, `Dojo.pathways`) except the team, `status` and `location`/`province`, which aren't self-service: an address edit is re-geocoded on save (`geo.geocoding.geocode`, same tolerant-failure pattern as `dojos.search.resolve_search_origin` — a failed/no-match geocode never blocks the save) and a successful one also refreshes `province` via `geo.geocoding.find_province` (point-in-polygon against `geo.AdministrativeBoundary`, with a nearest-boundary fallback), so a champion never touches either field directly.

**Events**: `dojos.views.dojo_event_list`/`dojo_event_create`/`dojo_event_set_status` (views live in `dojos`, not `events`, matching the rest of this admin area — same as `dojo_dashboard` reaching directly into `events.Registration`) manage `events.Event` rows for one dojo. `Event.status` (`events/models.py`) is a three-state lifecycle — `draft` (model default; hidden from the public site via `EventQuerySet.visible()`, used by every public-facing query: `event_list`, `upcoming_available_events`, `dojo_detail`'s `next_event`, `dojos.search.attach_next_events`) → `open` (registrations open, `Event.registration_open`) → `closed` (registrations closed, gated in `events.views.event_signup`). It is *not* a one-way lifecycle: `dojo_event_set_status` (POST-only) takes an absolute target `status` and sets it from any other status — the team can reopen a closed session or pull one back to draft, and existing registrations are always kept. The events list shows a one-click next step per row (Publish / Close registrations / Reopen); the event detail page (`dojo_event_detail`, edit-in-place like `dojo_manage`) shows every option in its status card, and posts `next` back to itself (validated with `url_has_allowed_host_and_scheme`). Saving the edit form never touches status. `events.forms.EventForm` (used by `dojo_event_create` and `dojo_event_detail`) has four quirks worth knowing before touching it: (1) it takes a single `event_date` field plus separate `start_time`/`end_time` *time* fields (not two datetimes) — a session can't span midnight, and this makes that structurally true rather than validated; all three render in Belgian dd/mm/yyyy + 24h HH:MM notation regardless of the visitor's own browser locale (`EventForm.save()` combines them back into the model's real `start_time`/`end_time` datetimes). (2) Its banner `image` can come from an upload or from `template_image`, a picker over `events.template_images.TEMPLATE_IMAGES` (linked from the shared image library, not copied, see "Standard images" below; the edit form preselects the one in use) (also the source seed data uses, see `seed_events.py`) — an uploaded file always wins if both are submitted. (3) `Event.team` is a `ManyToManyField` to `dojos.DojoMembership` (who runs the session — champion, mentors and youth mentors), rendered as a checkbox list scoped to the dojo's active memberships, labelled "Name (Role)", in `EventForm.__init__`. (4) `Event.pathways` is pre-selected from `Dojo.pathways` on a *new* event only (an existing event keeps its own); any pathway may be picked, the dojo's are just the default.

**Attendance**: `Registration.attended` is tri-state (`None` = not yet marked). `dojos/partials/_attendance.html` (built by `dojos.views._attendance_context`: confirmed, non-waitlisted registrations only, alphabetical) is shared by the dashboard (next upcoming session, else most recent) and `dojo_event_attendance` (a specific event, linked from its detail page's "Take attendance"). It's server-driven htmx, **not** `CoderDojo.initAttendance` (that bundle.js helper only toggles client-side and saves nothing — don't wire it up on these pages): each row's toggle posts to `dojo_event_attendance_mark` (`attended=present|absent|none`; re-clicking the pressed button sends `none`), which returns that row plus the "N of M present" summary as an `hx-swap-oob` fragment; "Mark all present" (`dojo_event_attendance_mark_all`) re-renders the whole block. Both fall back to a redirect for non-htmx posts, and resolve the registration scoped to the URL's event (and that event to the owned dojo). Each row also carries the per-ninja pathway picker (`dojo_event_registration_pathways`) and, with `AWARD_BELTS`, an "Award belt" form (`dojo_event_award_belt`); marking attendance (single or all) calls `events.awards.sync_milestones` so milestone badges follow it. The session's team (`Event.team`) is on the same list, under the children (`_attendance_team_row.html`, `dojo_event_team_attendance_mark`, stored in `events.TeamAttendance`, tri-state like `Registration.attended`; "Mark all present" includes them): who was actually there is the record the insurance needs. A child whose home dojo is another dojo is labelled "Visiting". Belts and badges are only ever awarded through `events/awards.py` (`award_belt` raises `BeltError` with a user-facing message) — `NinjaBelt` is an append-only history, never edited.

### Live notifications: Django Channels over Redis

The admin sidebar's notification bell (`dojos/templates/dojos/partials/_notification_bell.html`) is backed by `notifications.Notification` — `recipient` + `read` live on the same row, so per-user read state falls out for free; `dojo` (nullable FK) is what the admin panel of someone on several dojos' teams filters on, via `dojos.views._notification_context`. A dojo-level event that concerns more than one person fans out to one row per recipient sharing the same `dojo`/`text`/`url`, each independently read/unread.

**Creating a notification**: always through `notifications.services.notify(recipient, text, url="", dojo=None, params=None)` — never `Notification.objects.create()` directly. `text` is a `gettext_lazy` message with its `params`, rendered in the recipient's language (see "i18n"). It creates the row (the source of truth) and then best-effort nudges that recipient's live connection via the channel layer; a channel-layer failure is swallowed, same fail-open spirit as `CACHES`' `IGNORE_EXCEPTIONS`. Dojo-level events notify the dojo's managers through `dojos.team.notify_managers(dojo, text, url)` (one row per active champion/mentor, never youth mentors): a mentor application against a specific dojo (`applications.views.register_helper`), a waitlist promotion (`accounts.views.cancel_registration`) and a join request; individual team changes (accepted, added, declined, champion handed over) notify the person concerned via `notify` directly.

**Live push is WebSockets via Django Channels**, not SSE/polling — `daphne` (top of `INSTALLED_APPS`, so `manage.py runserver` transparently serves ASGI instead of WSGI), `ASGI_APPLICATION`/`CHANNEL_LAYERS` in `website/settings.py` (the latter is `channels_redis`, same `REDIS_HOST`/`REDIS_PORT` as `CACHES` but db 1, not 0), and `website/asgi.py`'s `ProtocolTypeRouter` (http → normal Django, websocket → `notifications.routing.websocket_urlpatterns` behind `AllowedHostsOriginValidator(AuthMiddlewareStack(...))`, so `scope["user"]` is the same session-authenticated user a normal request would see). `notifications.consumers.NotificationConsumer` checks admin access (an active champion or mentor, `dojos.access.dojo_role`) once at `connect()` (closes the socket on a mismatch, same 404-not-403 reasoning as `dojos.access.require_dojo_access`) and, on every group event, re-renders `_notification_bell.html` fresh from the DB and pushes it as one `hx-swap-oob="true"`-wrapped fragment — `htmx-ext-ws` (loaded in `_admin_base.html`) does the DOM swap from that alone, no client-side JSON handling. The bell's own `ws-connect` lives on a separate, never-swapped `<div>` in `_admin_base.html` specifically so the bell's own oob updates (and `mark_all_notifications_read`'s htmx response, which reuses the identical oob-id-matching trick) never tear down the socket that's delivering them.

If you add a Channels consumer that touches the database, test it with `TransactionTestCase`, not `TestCase` — the consumer's DB access runs on a separate thread (`channels.db.database_sync_to_async`) with its own connection, which a `TestCase`'s wrapping transaction (held on the main thread's connection) is invisible to. `notifications.tests`/`dojos.tests.NotificationConsumerTests` are the reference examples, including `@override_settings(CHANNEL_LAYERS=...InMemoryChannelLayer...)` so consumer tests don't need a real Redis.

`django-debug-toolbar`'s `CachePanel` and `TemplatesPanel` are disabled (`DEBUG_TOOLBAR_PANELS` in `website/settings.py`, dev-only either way) — both do unsafe lazy model stringification while serializing call/context args for display (cache-call args for `CachePanel`; every template context value for `TemplatesPanel` — any model whose `__str__` queries related rows), which is merely wasteful under WSGI but hard-errors every single page it touches (`SynchronousOnlyOperation`) now that requests are served over ASGI. Any other panel that stringifies arbitrary model instances is a candidate for the same bug if it starts erroring — these two are just the ones actually hit so far.

**A model's `__str__` never queries**, for the same reason: under ASGI, a lazy foreign-key lookup inside `__str__` raises `SynchronousOnlyOperation` wherever something stringifies a row from an async context. So a model whose `__str__` names a related object preloads it in its default manager, the plain Django way: a `Manager` subclass whose `get_queryset()` adds `select_related(...)` (built with `Manager.from_queryset(...)` when the model has its own QuerySet, e.g. `EventManager`, `DojoManager`). A new model whose `__str__` follows a relation does the same; `core.tests.StrNeverQueriesTests` lists every such model.

### Geo search: MySQL spherical distance

`django.contrib.gis`'s `Distance()` only gets proper spherical/spheroidal math substituted on PostGIS — on MySQL it silently returns a raw planar-degree value. `geo/functions.py` defines `DistanceSphere`, a `GeoFunc` subclass wrapping MySQL's `ST_Distance_Sphere`, so the real distance is still computed in the database rather than in Python. **Always use `geo.functions.DistanceSphere` for any new distance-based query against `PointField`s — never Django's built-in `Distance()`, and never compute distance in Python.** See `dojos/search.py` (`dojos_by_distance`) for the reference usage: annotate with `DistanceSphere(F("location"), origin) / 1000.0` and order by it.

The dojo-finder search (`dojos/search.py`) resolves an "origin" point with a fixed priority: typed address (geocoded via `geo.geocoding.geocode`, a thin Nominatim/OpenStreetMap client restricted to Belgium) > browser-supplied lat/lon ("use my location") > the logged-in account's postcode (`User.postal_code`, optional; `dojos.search.postal_code_origin` averages that postcode's `geo.Municipality` centres) > a hardcoded Ghent default. Only the Ghent default is cached (`dojos_by_distance` checks the origin's identity), so one family's list never leaks to another visitor. It's shared by both the full dojo-finder page and the homepage's embedded widget — `core.views.home` calls the same `resolve_search_origin`/`dojos_by_distance` helpers.

### htmx widgets, not a JS SPA

Per-project convention: reach for htmx for anything that needs server-driven partial updates; use native HTML/CSS for pure client-side behavior (toggles, etc.); only hand-write JS when neither covers it (hardware APIs, instant local state, scroll/viewport-only logic). `core.views.home` is the clearest example — it renders initial state for two independent htmx-driven widgets that each re-fetch themselves against their own endpoint rather than the page reloading:
- **Dojo finder** (`dojos.views`, form in `dojos/forms.py`) — searches post to a widget view that re-renders just the results partial.
- **Upcoming sessions carousel** (`events.views.upcoming_sessions_widget`, paged via `events.search.upcoming_available_events` / `WIDGET_PAGE_SIZE`) — further pages lazy-load over htmx as it's scrolled.

### Email

**Every mail goes through the mail engine** (`mailing.services.send`, queued and sent by the Celery workers; see "Mailing and segmentation"). Nothing calls `send_mail` directly: the onboarding mails in `applications.services` and the password reset (`accounts.forms.StyledPasswordResetForm.send_mail`) are `service` templates like any other, sent through `send_or_log` so a missing template is logged instead of failing the reviewer's action or the reset. `EMAIL_BACKEND` is env-driven in `website/settings.py`: console backend by default (host dev), SMTP once `EMAIL_HOST` is set. The devcontainer points it at **Mailpit** (`mailpit` service in `.devcontainer/docker-compose.yml`, SMTP on `mailpit:1025`, no auth/TLS), which catches every outgoing mail: during development and testing all mail goes there, and its UI is where you check it. Mailpit also serves as the dev bounce mailbox over POP3 (`mailpit:1110`, `MP_POP3_AUTH`) and has chaos mode on (`MP_ENABLE_CHAOS`) to simulate SMTP failures; both need the `mailpit` container recreated after changing its environment (from the host: `docker compose -f .devcontainer/docker-compose.yml up -d mailpit`). Read them at `https://coolregistration.localhost/mails/` (nginx proxies `/mails/` to Mailpit's UI; `MP_WEBROOT=/mails` has to match that prefix), or directly on the host at `http://localhost:8025/mails/`. Mail is kept on the `mailpit-data` volume (max 5000 messages).

### Background jobs: two Celery workers, beat embedded

Celery (`website/celery.py`, loaded from `website/__init__.py` so `@shared_task` binds to it) runs background and scheduled work. Configuration is the `CELERY_*` block in `website/settings.py` (`config_from_object(..., namespace="CELERY")`):

- **Two workers, two queues** (kept lean, same in dev and production; design in `DATA_MODEL.md` §11, "Production: two Celery workers under systemd"):
  - The `periodic` worker (`-Q periodic -B`) runs beat embedded, plus every task beat triggers. `CELERY_TASK_ROUTES` is built from `CELERY_BEAT_SCHEDULE`, so a scheduled task is routed to `periodic` automatically.
  - The mailing worker (`-Q celery`) runs everything else on the default queue. A new task needs no routing.
  - Both run with concurrency 1. Keep periodic jobs short: a slow one holds up the 10-second mail dispatcher, so a heavy job only enqueues its real work on the default queue. Never add `-B` to the second worker, or every job fires twice.
- **Broker:** Redis db `CELERY_BROKER_DB` (default 2). The cache is db 0 and Channels db 1, so a `cache.clear()` can't drop queued tasks.
- **Delivery:** `acks_late` plus `reject_on_worker_lost` (and a prefetch of 1), so a task whose worker dies halfway is handed out again. Write tasks to be safe to run twice.
- **Results:** `CELERY_TASK_IGNORE_RESULT = True`. Tasks report through the rows they change (e.g. `EmailMessage.status`), not through results. The `django-db` result backend stays configured for any task that opts in with `ignore_result=False`. `CELERY_TASK_TIME_LIMIT` is 30 minutes.
- **Time zone:** `CELERY_TIMEZONE = "Europe/Brussels"`, so crontab schedules are in Belgian local time. Django itself stays on `TIME_ZONE = "UTC"`.
- **Schedule:** `CELERY_BEAT_SCHEDULE` in settings is the only place jobs are defined (no `add_periodic_task` calls). Beat uses `django_celery_beat`'s `DatabaseScheduler`, which copies that dict into the `PeriodicTask` table at startup; you can edit it in the Django admin (*Periodic tasks*). It never deletes an entry the code stopped defining: remove stale ones with a data migration, as `mailing/migrations/0005_…` does. Beat only *sends* a task by name; a misspelled name shows up in the worker log as "Received unregistered task".
- **Tasks:** `autodiscover_tasks()` picks up each installed app's `tasks.py`: `mailing/tasks.py` (the mail queue, bounces, automated mail, campaigns, journeys) and `events/tasks.py` (the nightly engagement rebuild).

**Dev processes:** `.devcontainer/start.sh` starts both workers in the background before `runserver`, logging to `/workspace/celery-periodic.log` and `/workspace/celery-mailing.log` (gitignored). Nothing supervises or autoreloads them, unlike `runserver`: **after changing a task or the schedule, restart them**, or they keep running the old code (a stale worker is exactly how you get "unregistered task" errors). From a workspace shell (run the `pkill` on its own: `pkill -f` also matches a shell whose command line contains the pattern):

```sh
pkill -f "[c]elery -A website worker"
celery -A website worker -n periodic@%h -Q periodic -c 1 -B --scheduler django_celery_beat.schedulers:DatabaseScheduler -l INFO > celery-periodic.log 2>&1 &
celery -A website worker -n mailing@%h -Q celery -c 1 -l INFO > celery-mailing.log 2>&1 &
celery -A website inspect active_queues   # which worker listens to which queue
celery -A website inspect registered      # what the running workers actually know
```

**Production:** the same two workers run as systemd *user* services, installed and restarted by every `scripts/deploy.sh` run (see "Deploying"); dev starts them from `start.sh`. Level27's Redis is the broker. They share the machine's memory with gunicorn, so they recycle their child processes and run at lower priority. **Every mail the site sends goes through them**: if they're down, mail waits in the queue (nothing is lost).

**Tests:** no `CELERY_TASK_ALWAYS_EAGER` override exists. Test a task by calling the function directly (`send_pending_emails()`), not `.delay()`, which would need a broker.

### Mailing, segmentation and the organisation dashboard

`mailing` is the site's mail engine: every mail goes through it, and campaigns are run from the organisation dashboard. `DATA_MODEL.md` §11 has the diagrams and **the plan it was built from** (every phase is done; the decisions and open points are there too): mail categories with opt-in/out, the `send()` gateway, the engagement snapshot, the segmentation attributes, `Event.audience` (a label for girls' sessions, never a signup restriction), and the phases. Follow that plan and update it as phases land.

- **Account data it uses:** `User.preferred_language` (the mail language; set at family sign-up, defaulting to the page's language; empty = English) and `User.postal_code` (optional, a Belgian postcode checked against `geo.Municipality`; also the dojo finder's default origin, see "Geo search"). `Ninja.gender` (`girl`/`boy`/`other`/`unspecified`, default `unspecified` = "Prefer not to say") is optional on every family form (sign-up child rows, add a child, edit a child; `accounts.views._clean_gender` turns anything unknown into `unspecified`, and an edit without the field keeps the stored value). `Event.audience` (`everyone`/`girls`) is a "Girls' session" label on the public pages (`events/partials/_audience_badge.html`) and a targeting signal, **never** a signup restriction.
- **Categories** (`mailing/categories.py`, `MailCategory`): `service`, `registration`, `reminder`, `dojo_news`, `volunteer`, `newsletter`. A code enum, not a table. Per category: `CAN_OPT_OUT` (service/registration can't be switched off), `DEFAULT_SUBSCRIBED` (newsletter off until opted in, the rest on), `PRIORITY` (lower is sent first) and `ALLOWED_FOR_NINJA_ACCOUNTS` (a ninja's own login gets service/registration/reminder/dojo_news, never volunteer or newsletter mail).
- **Segments** (`Segment` → `SegmentGroup`s, nested through `parent`, each ANDing or ORing its rules and child groups → `SegmentRule`s `attribute`/`operator`/`value` JSON) describe an audience without code. A group's `scope` is `user` (rules filter accounts) or `ninja` (every rule describes *the same child*, and the group selects that child's guardians); a ninja group can only contain ninja groups. `mailing.segmentation.resolver.SegmentResolver.resolve(segment)` returns the accounts, always limited to **active adult accounts with an email**, never ninja accounts; the root groups are ANDed, and a segment without rules resolves to nobody. **Every rule becomes its own `pk__in` subquery**, never a join in one `filter()`, so two rules over the same to-many relation stay independent. Keep it that way when touching the resolver.
- **Attributes** are `SegmentAttribute` subclasses (`mailing/segmentation/base.py`: `key`, `label`, `value_type`, `scope`, `choices()`, `build_q(operator, value) -> Q` on the scope's model, and `validate()`; the operators per `value_type` are in `OPERATORS`). They're registered by key in `mailing/segmentation/registry.py`. Today, on accounts: `account_role` (parent / active mentor / active champion / organisation role; one account can be several), `joined_within_days`, `account_type`, `has_children`, `active_team_member` (active champion/mentor membership at an active dojo that held a non-draft session in the last N days), `language`, `province` (including a `brussels` choice, since Brussels-Capital isn't a province in `geo.AdministrativeBoundary`), `near_dojo` (`{"dojo": id, "km": n}` from the postcode's municipality centres, via `DistanceSphere`), `ninja_gender`, `ninja_age`, `ninja_home_dojo`, `current_belt` (with a "No belt yet" choice), `has_badge`, `pathway`, `waitlisted_for_event`, `cancellations` (last 90 days, from `events.RegistrationCancellation`), `attended_within_days` (came to a session in the last N days: marked present, or a confirmed place where the dojo marked nobody), `event`, `attended_event`, and on the engagement snapshot: `engagement_stage`, `engagement_stage_at_dojo` (`{"dojo": id, "stages": [...]}`), `attendance_rate` (%), `sessions_attended`, `missed_in_a_row`, `days_since_last_visit`, `no_shows`, `has_upcoming_registration`, `main_dojo_status`. Value types: `choice`, `boolean`, `days`, `number` (`gte`/`lte`), `distance`, `dojo_stage`; each attribute also has `describe()` (the rule as a sentence) and `value_from_form()` (the builder's fields → the JSON value). `SegmentRule.clean()` validates a rule against its attribute and its group's scope. A new criterion is a new attribute class plus a registry entry; the resolver doesn't change.
- **Templates** (`EmailTemplate`): one row per `key` and `language`, with a `category`, a subject and a plain-text body in Django template syntax. `mailing.rendering.render(key, language, context)` returns `(subject, body)`, falls back to English when a language is missing, doesn't HTML-escape, and formats `|date` under the template's language (so day and month names are translated). The standard templates and a working sample context for each key are in `mailing/seed_templates.py` (`TEMPLATES`, `SAMPLE_CONTEXT`; `SYSTEM_TEMPLATE_KEYS` = the ones the site sends itself): booking confirmed/waitlisted, waiting-list promotion, session reminder, new sessions at a dojo, the five onboarding mails, the password reset, a child's new login, a child made youth mentor (to the family), and the three campaign examples, each in en/nl/fr.
- **Campaigns** (`Campaign`, rules in `mailing/campaigns.py`; `CampaignError` carries a user-facing message) are one mailing to a segment: a `category` (only one people can opt out of), a `template_key`, a `context` of extra template variables and an optional `scheduled_at`. `draft → queued → sending → completed` (or `cancelled`). `launch()` checks the campaign (`launch_problems`), freezes the segment's definition in `segment_snapshot` (`serialize_segment`) and marks it `queued`; the audience is always resolved from that snapshot, so editing the segment later changes nothing for a launched campaign. `launch_due` (beat, every minute, `periodic`) hands due campaigns (no `scheduled_at`, or its time has come) to the `launch_campaign` task (default queue), resumes one whose queuing was interrupted and completes those whose mail is all out. `queue_mail` queues one mail per account that wants the category, through `send()` with idempotency key `campaign:<id>:<user>` and a cache lock, so re-running is safe. `cancel` withdraws mail not yet sent. `send_test` sends the mail to its author (`EmailMessage.is_test`, subject "[Test] …", the author's preferences don't apply, blocks do). `stats` gives the results page's numbers. `seed_mailing` seeds three drafts: *Coolest Projects* ("Everyone active": the two activity attributes ORed, with the same `ACTIVE_WITHIN_DAYS` = 365), *CoderDojo Girlz* (families with a girl or a child whose gender isn't listed) and *New dojo opening* (families within 20 km of a new dojo).
- **The organisation dashboard** (`/manage/…`, `mailing/manage.py`, shell `core/_manage_base.html`, organisation `admin` role only via `accounts.organisation.require_organisation_admin`, 404 otherwise; the nav's *Organisation* link goes there for that role, the board still gets the Django admin): *Campaigns* (list with results, create/edit a draft with template variables as `name: value` lines, preview in every language, audience count and sample, send a test, launch, cancel) and *Segments* (list with counts, and a builder: groups about accounts or about "the same child", all/any, nested groups, rules added through fields that fit the attribute via htmx `segment_rule_fields`, each shown as a sentence from `SegmentAttribute.describe`, values read with `value_from_form`; live count and sample) *Journeys* (list, create, preview, test, activate/pause, results and who gets it on the next run), and *Mail templates* (every template with its languages and what uses it; edit one language at a time with a preview on `SAMPLE_CONTEXT` example data, the subject and body checked by `TemplateVersionForm` so a broken template is never saved; a missing language starts from the English text; create campaign templates; delete a language version or a campaign template, never the English fallback, a template the site sends itself (`SYSTEM_TEMPLATE_KEYS`) or one a draft or queued campaign still uses). All of them also keep their full Django admin pages, for fixing things by hand. The same shell has a *Public site* group with *Promotions* (`content/manage.py`, see "Organisation-run events" above).
- **Consent** (`mailing/preferences.py`): `MailPreference` is an account's choice per category (no row = the default); `ConsentEvent` is the append-only log of every change (who, what, when, source, `PRIVACY_WORDING_VERSION`), written only by `set_preference(user, category, subscribed, source)`. Never write either model directly. `is_subscribed()` answers for one account, `subscribed_q(category)` filters a `User` queryset in the database. `EmailSuppression` blocks an address whatever its preferences (hard bounce, complaint, by hand). The approved privacy explanation is one partial, `mailing/partials/_privacy_explanation.html`, shown on the Mail preferences page and next to the newsletter opt-in on family sign-up; change its wording only together with `PRIVACY_WORDING_VERSION`.
- **`send(user, category, template_key, context, idempotency_key=None, campaign=None, send_after=None)`** (`mailing/services.py`) is the only way to send mail. It renders the template in the account's language right away (the row is the record of exactly what was sent; `recipient_name`, `site_url` and, for opt-out categories, `unsubscribe_url` are added to the context) and inserts an `EmailMessage`: `pending`, or `suppressed` with a `status_reason` (inactive account, category not for this account type, not subscribed, no address, blocked address). An `idempotency_key` makes a repeat call a no-op. It never talks to SMTP and never calls `.delay()`. Links in mail use `settings.SITE_URL` (there's no request in a worker).
- **The database is the mail queue** (`mailing/tasks.py`). `send_pending_emails` (beat, every 10 s, `periodic` queue) only dispatches: it claims pending rows by `priority`, `created_at` with `select_for_update(skip_locked=True)`, never more than `MAILING_CLAIM_LIMIT` in flight, marks them `sending` and hands them out as a `group` of `send_email_batch` subtasks (`MAILING_BATCH_SIZE` each). `send_email_batch` (default queue) sends a chunk over one SMTP connection; Celery does the throttling (`rate_limit=MAILING_BATCH_RATE_LIMIT`) and the retries (`autoretry_for=TransientSendError`, backoff from 30 s up to 10 min, 5 retries; `SendBatchTask.on_failure` fails what's left after the last one). Each row is marked `sent` right after its own send, so a retry never mails anyone twice; a 5xx about one recipient fails only that row. Mail is built as `QueuedEmail`, which allows 998-character header lines: otherwise the email package RFC 2047-encodes the long `List-Unsubscribe` URL and one-click unsubscribe breaks. Opt-out categories get `List-Unsubscribe` and `List-Unsubscribe-Post` (RFC 8058). `requeue_stuck_emails` (beat, every 15 min) puts rows `sending` for more than `MAILING_CLAIM_TIMEOUT_MINUTES` back and logs the queue's state.
- **Pages** (`mailing/urls.py`): `/account/mail/` (`mail_preferences`, login required) has a checkbox per category the account can switch off, the mail language and (adults) the postcode, linked from the account page. `/mail/unsubscribe/<token>/` (`mail_unsubscribe`) needs no login: the token is `django.core.signing` of user + category (salt `mailing.unsubscribe`, no expiry). GET confirms, POST unsubscribes (one category, or `scope=all`). It's `csrf_exempt` because mail providers' one-click POST carries no CSRF token; the signed token is all it trusts.
- **Bounces** (`mailing/bounce.py`, the `process_bounces` beat task every 5 min, off while `MAILING_BOUNCE_IMAP_HOST` is empty). Every mail's envelope sender is `MAILING_BOUNCE_ADDRESS` (with `{id}` → the row id for VERP when the host takes plus-addressing); the `From` header people see stays `DEFAULT_FROM_EMAIL`. `BounceProcessor` (connect → get_new_messages → parse → handle) reads the bounce mailbox over IMAP (`ImapMailbox`, production) or POP3 (`Pop3Mailbox`, the devcontainer, where Mailpit is the mailbox), chosen by `MAILING_BOUNCE_PROTOCOL`. It parses DSNs (RFC 3464) and complaint reports (ARF), plus plain-text bounces that quote our Message-ID and a status code; auto-replies and anything else are skipped. Matching is by VERP address, else by our `message_id`. Each result is a `BounceRecord`. A hard bounce marks the mail `bounced` and adds an `EmailSuppression`; `MAILING_SOFT_BOUNCE_LIMIT` soft bounces within the window suppress too; a complaint switches off the account's optional categories (ConsentEvent source `bounce`) without blocking account or booking mail. `ProcessedImapMessage` records every handled message per mailbox, so none is handled twice; nothing is ever deleted from the mailbox.
- **Registrations and cancellations:** `Registration.created_at` is when the ninja was signed up. Cancelling (`accounts.views.cancel_registration`) still deletes the `Registration`, so places and the waiting list work as before, but first appends an `events.RegistrationCancellation` (ninja, event, whether it was waitlisted, when it was signed up and cancelled, by whom), the log the `cancellations` attribute reads.
- **Engagement snapshot** (`events/engagement.py`, model `events.NinjaEngagement`): how each child comes to sessions, rebuilt every night at 03:00 by `events.tasks.rebuild_engagement` (default queue) and on demand by `manage.py rebuild_engagement` (`start.sh` runs it after seeding). One row per child and dojo they came to in the last year, plus an overall row (`dojo` empty) measured at their main dojo (home dojo, else the one they visited most) that counts visits anywhere. Only sessions meant for the child count as offered (`is_aimed_at`: age range, a girls' session only for girls); "came" is marked present, or a confirmed place at a session where the dojo marked nobody (`from_marked_attendance` records that). Stages, first match wins: aged out, never came, new, lapsed, at risk (`AT_RISK_MISSED` = 3 in a row), regular (`REGULAR_MIN_VISITS` = 3 and `REGULAR_MIN_RATE` = 0.5 in `WINDOW_DAYS` = 180), occasional; the thresholds are constants at the top of the module. The dojo team's attendance rows show the child's stage at that dojo, with the figures as a tooltip (`dojos.views._attendance_context` → `engagement_by_ninja`, looked up with `core`'s `get_item` filter). It's rebuilt wholesale, so an edit in the admin only lasts until the next night.
- **Change over time and journeys** (Tier 3). Each nightly engagement rebuild compares every child's overall stage with the previous night's and appends a `events.NinjaEngagementChange` (from, to, day; not on the very first build, and never twice for one day). The `stage_changed` attribute (`{"from": [...] or [], "to": [...], "days": N}`) reads it, alongside `no_new_belt_within_days` (children) and `not_on_team_within_days` (accounts, via `Event.team`). A **journey** (`mailing.Journey`, service `mailing/journeys.py`, dashboard *Journeys*) is a standing campaign: `run()` (beat `run_journeys`, daily 18:00, default queue, after the 03:00 rebuild) sends its mail through `send()` to everyone who matches its segment that day, wants its kind of mail and hasn't had it within `cooldown_days` (checked against `JourneyDelivery`, one row per mail); paired with a `stage_changed` rule it's a triggered mail ("we miss you" the week a child becomes at risk). Journeys start paused; `activate` runs the same checks as a campaign launch (`launch_problems`).
- **Automated mail** (`mailing/automated.py`; every one goes through `send()`). A ninja's mail goes to the family (`family_of`: every guardian, plus the ninja's own login when it has an email). `booking_mail` (from `events.views.event_signup`, in the sign-up's transaction: `registration_confirmed` or `registration_waitlisted`) and `waitlist_promoted_mail` (from `accounts.views.cancel_registration`) are `registration` mail. Two daily beat jobs run on the default queue (their beat entries set `options.queue`, so `CELERY_TASK_ROUTES` leaves them off `periodic`): `send_session_reminders` at 09:00 (`reminder`, sessions `MAILING_REMINDER_DAYS_BEFORE` = 2 days ahead) and `announce_new_sessions` at 17:00 (`dojo_news`, one mail per family and dojo for sessions that opened since the last run; a family belongs to a dojo through a child's home dojo or a visit in the last `MAILING_DOJO_NEWS_ACTIVE_DAYS`). `Event.published_at` is set in `Event.save()` the first time a session opens; `announced_at` is set by the digest. Every automated mail has an idempotency key, so re-running a job queues nothing twice. A missing template is logged and skipped, never an error for the family. The templates reach production through `manage.py load_mail_templates` (create-only, never overwrites), which `deploy.sh` runs after `migrate`; `seed_mailing` calls it too.
- **Testing mail by hand** (devcontainer): all mail goes to Mailpit, whose UI at `https://coolregistration.localhost/mails/` is where you check it. `manage.py simulate_bounce [id] --kind hard|soft|complaint [--process]` (DEBUG only) sends a realistic bounce report for a sent mail into Mailpit, where `process_bounces` finds it over POP3. Mailpit's chaos mode (`PUT /mails/api/v1/chaos`) makes it refuse mail, to watch retries and failures.

- The mail log, bounces and suppressions are only in the Django admin (technical tools, no dashboard page planned).

### Sensitive vs. public media

`MEDIA_ROOT`/`MEDIA_URL` (photos, icons, event images) are public and served directly under `DEBUG` (`website/urls.py`). `PRIVATE_MEDIA_ROOT` (background-check documents only) has no corresponding `url()` pattern anywhere — don't add one. If a new feature needs to store a sensitive file, use `applications.storage.private_storage` (or the same `base_url=None` pattern) and gate reads through a permission-checked view, not a media URL.

### Standard images: link, don't copy

The app ships standard images for event banners, dojo icons, award icons, mentor and ninja avatars and pathway images. Each set lives under its app's `static/` folder with a module listing its `(filename, label)` pairs: `events.template_images` (banners), `dojos.template_icons` (dojo icons), `accounts.template_avatars` (`TEMPLATE_AVATARS` for adults, `TEMPLATE_KID_AVATARS` for ninjas). Badge icons (`events/seed_data/awards/`) and pathway images (`pathways/seed_data/images/`) stay seed data: they're designed and enabled by the team, not picked by users. `core/image_library.py` maps each kind to its folder (`LIBRARY_DIRS`). **Using one never copies it:** `use_library_image(instance, field, kind, filename)` points the `ImageField` at `library/<kind>/<filename>` in media storage, which is copied there once, the first time any row uses it (no deploy step). Every row that picks the same template shares that one file. Only a file someone uploads themselves goes through the field's `upload_to` and gets its own copy. The form pickers (`DojoProfileForm.template_icon`, `EventForm.template_image`, the ninja avatar dropdown in `accounts.views`) and every seeder use it, and `library_filename(fieldfile, kind)` preselects the current template in a picker. Library files are shared: never `.delete()` one through a model field (`is_library_image()` tells the two apart). Tests that save files mix in `core.testing.TempMediaMixin` (a throwaway `MEDIA_ROOT`; the test's own `setUp` must call `super().setUp()`).

### i18n

`LANGUAGES` is `en-us`/`nl-be`/`fr-be` (German was dropped until German texts can be checked; also the mail languages, `User.preferred_language`). `LocaleMiddleware` picks the language (session, then the browser's `Accept-Language`); the switcher in `core/templates/core/menu.html` posts to `set_language`. **The site's texts live in one project catalog per language, `locale/{nl_BE,fr_BE}/LC_MESSAGES/django.po`** (`LOCALE_PATHS`); the compiled `django.mo` is committed (the server may have no gettext), so after editing a `.po` run `compilemessages` and commit both.

- **A dojo's own texts are in the dojo's languages** (`DATA_MODEL.md` §19): `Dojo.languages` (ordered, first = main language; also the languages its sessions are given in, shown and filterable), and `Dojo`/`Event`/`Announcement` are `core.content_languages.TranslatableModel`s: main language in the normal columns, others in `translations`. Show them with `{% load content_i18n %}` `{{ obj|localized:"field" }}` (+ `{% only_in text %}` for the fallback note), never the raw field on a public page; forms add the per-language fields with `add_translation_fields`/`save_translation_fields` and include `dojos/partials/_translation_fields.html`. A new translatable text is a `TRANSLATABLE_FIELDS` entry, not a new column. The organisation's own content does the same in `settings.ORGANISATION_LANGUAGES` (`OrganisationContent`: pathways, steps, projects, skills, belts, badges, team listing, promotions; `ScopedContent`: FAQs and testimonials follow their dojo when scoped to one), edited through `core.admin_translations.TranslationAdminMixin` in the admin (put it first in a ModelAdmin's bases for any new translatable model).
- **Everything a person sees is translated:** every template (public, family, volunteer applications, the dojo team dashboard, the organisation dashboard), the Python texts they show (forms, messages, model choices, `TeamError`/`OnboardingError`/`CampaignError`/`BeltError`/`ChildAccountError`, the segment builder's attribute labels, operators and rule sentences), dashboard notifications and `bundle.js`. **Not translated through the catalogs:** anything stored in the database; the dojo's own texts follow its languages (above), so does the organisation's content (pathways, FAQs, badges, belts, testimonials, team listing, promotions); segment and template descriptions are shown as written; model `help_text`/`verbose_name` (the Django admin, which Django itself translates); mail templates (their own rows per language).
- **Notifications are stored text**, so `notifications.services.notify(recipient, gettext_lazy("... %(dojo)s ..."), params={...})` renders them in the *recipient's* `preferred_language`, not the acting user's; `dojos.team.notify_managers` passes `params` through. Never pass an f-string or an already-translated `_()` string.
- **`bundle.js`** uses Django's JavaScript catalog: `jsi18n/` (`JavaScriptCatalog`) is loaded before it in the three page shells, and it calls `gettext("...")` (falling back to the English text without the catalog). Its strings live in `locale/*/LC_MESSAGES/djangojs.po` (`makemessages -d djangojs`).
- **Tone:** Dutch uses informal "je" everywhere (also to parents); French uses "vous". Keep a text's HTML/placeholders identical in translations.
- **Marking texts:** `{% load i18n %}` in every template that has any (includes don't inherit it); `{% translate "..." %}` for plain text, `{% blocktranslate with x=... %}` for text with variables (no filters inside the block: bind them in `with`), `count counter=...` + `{% plural %}` for plurals. In Python, `gettext_lazy as _` for module-level strings (choices, form labels) and `gettext as _` in views, with named placeholders (`_("%(name)s ...") % {...}`), never f-strings. A lazy label that's joined or `.lower()`ed needs `str()` first. JS strings in a template: `{% translate "..." as var %}` then `"{{ var|escapejs }}"`, with `{name}` placeholders replaced in JS (a `%s` in a template `translate` string gets mangled). Never write a template tag inside a JS comment in a template: it's parsed.
- **Workflow:** `python manage.py makemessages -l nl_BE -l fr_BE --ignore=".venv/*" --ignore="docs/*" --ignore="staticfiles/*" --ignore="media/*"` (and the same with `-d djangojs` after changing `bundle.js`), translate the new entries and replace the *fuzzy* guesses gettext pre-fills (they're usually wrong, and `compilemessages` skips them), keep the header free of `#, fuzzy` (or the French plural rule is dropped), then `python manage.py compilemessages -l nl_BE -l fr_BE --ignore=".venv/*"`. Django's own texts (form errors, password rules) come translated from Django's catalogs. Mail templates are translated separately (`EmailTemplate` rows per language, `mailing/seed_templates.py`); the help docs too (`docs/`).
