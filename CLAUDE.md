# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Multiple AI agents/sessions may work in this repo. Keep this file authoritative and current: if you change something it describes (settings, workflows, conventions), update the relevant section in the same change rather than leaving it stale for the next agent.

## What this is

A Django site for CoderDojo Belgium: dojo discovery/search, event registration, self-service family accounts, account-level applications (champion / mentor) with a Belgian legal background-check workflow, dojo teams and their admin area, learning pathways, ninjas' badges and belts, and organisation roles for the management side (the Django admin). No separate frontend build — server-rendered Django templates plus [htmx](https://htmx.org/) for the dynamic bits (see Architecture below), a hand-maintained `core/static/core/{js,css}/bundle.{js,css}` (no bundler/npm in this repo), and vanilla CSS/HTML for anything that doesn't need a server round-trip.

## Workflow rules

`CODING_STANDARDS.md` gathers the coding standards, the linting setup, the guard tests, test coverage and complexity (with `quality/`, the measurement tooling, and which code is production and which is development-only); keep it current when a standard or tool changes. `MEMORY_PROFILE.md` is the memory used per function of the site (`quality/memory_profile.py`: tracemalloc plus `sys.monitoring` over every page and background job on a `seed_scale` database), with which functions are worth refactoring; rerun it after changing a background job or a page that lists many rows.

- **Always work inside the `.devcontainer`, never against the host Python/MySQL.** Before running `manage.py` commands (migrations, `runserver`, and especially `manage.py test`), check the stack is actually up — `docker ps` should show `coolregistration-dev-workspace`/`-db`/`-redis`/`-proxy` as `Up`; if it isn't, start it (`docker compose -f .devcontainer/docker-compose.yml up -d`) rather than falling back to a host-level run. Run commands via `docker compose -f .devcontainer/docker-compose.yml exec workspace <command>` (or `exec workspace bash` for a shell). This matters beyond convention: the notification bell's WebSocket support (Django Channels, see Architecture) depends on Redis and on `daphne` actually serving `runserver`'s ASGI app, both of which the devcontainer wires up for you — a host run can silently diverge (e.g. a stray host MySQL, or no Redis at all) without it being obvious from the command output alone.
  - **One exception: testing nginx's own behavior, or any real end-to-end check, has to go through the host.** `docker compose exec workspace` talks to Django directly and never touches the `proxy` container at all — TLS termination, the `/docs/` and `/mails/` (Mailpit) aliases, and (since adding WebSockets) the `Upgrade`/`Connection` proxy headers all live in nginx, not Django, so a workspace-only check can pass while the thing a real client actually hits is still broken. Verify those from the host against the real FQDN (`https://coolregistration.localhost`, `wss://coolregistration.localhost/ws/...`) — plain `127.0.0.1`/internal-port requests skip nginx *and* fail `ALLOWED_HOSTS`/origin checks that key off `coolregistration.localhost`. A hand-written test client also needs to send an `Origin` header matching that FQDN (a real browser always does this automatically) or Channels' `AllowedHostsOriginValidator` (see Architecture) rejects the connection with a 403 that has nothing to do with the thing you're actually testing.
  - **The devcontainer is a development system, not production.** Its data is seeded demo data, so clearing the Redis cache (db 0: `python manage.py shell -c "from django.core.cache import cache; cache.clear()"`) is always fine whenever stale cached data could explain what a page shows, e.g. after reseeding or changing cached data; no need to ask. That's the cache only: not the Channels layer (db 1) or the Celery broker (db 2), and never anything on the production server.
  - **Working from the host (outside the workspace container), make changes inside the container.** Many repo files are owned by root, because the container writes them (migrations, `.po`/`.mo` catalogs, docs, anything a `manage.py` command generated), so editing them from the host fails with "Permission denied", and so do new files in root-owned folders (e.g. `docs/`). Don't `chown` or `sudo` around it: run the change inside the container, e.g. `docker exec -w /workspace coolregistration-dev-workspace python /tmp/patch.py` after `docker cp`-ing the script (or the new file) in. Files your host user owns can still be edited from the host. If `docker compose -f .devcontainer/docker-compose.yml exec workspace ...` says `service "workspace" is not running` while `docker ps` shows the containers up, the stack was started under another compose project name: `docker exec coolregistration-dev-workspace ...` reaches the same container.
  - **The Django debug toolbar is only a development aid**, so it's fine to switch it off for a while when it gets in the way, no need to ask: it covers part of every page in a fresh browser (its "hide" cookie doesn't keep it closed), which spoils screenshots and layout checks. In a headless browser, inject `#djDebug, #djDebugRoot { display: none !important; }` into each page (the toolbar's root also intercepts clicks); for the whole dev site, make `_show_debug_toolbar` in `website/settings.py` return `False` and put it back afterwards. It never runs in production (`DEBUG` is off there).
  - **Git inside the container commits as Claude** (`Claude <noreply@anthropic.com>`, the `GIT_AUTHOR_*`/`GIT_COMMITTER_*` variables on the `workspace` service in `.devcontainer/docker-compose.yml`), so its commits are told apart from a person's commits made on the host. Each of those four variables takes its value from the environment that runs `docker compose` (or `.devcontainer/.env`) when it's set there, and falls back to Claude otherwise; a change needs the `workspace` container recreated (`up -d workspace`).
  - **Line endings are LF everywhere, also on a Windows checkout** (`.gitattributes`: `* text=auto eol=lf`, CRLF only for `*.bat`/`*.cmd`, binaries marked `binary`; `.editorconfig` makes editors create LF files). The working tree is bind-mounted into the Linux containers, where a CRLF shell script fails (`bash\r: not found`). A new binary file type gets its `binary` line in `.gitattributes`. A Windows clone made before `.gitattributes` existed fixes itself with `git rm --cached -r . && git reset --hard` (after committing or stashing work). `AGENTS.md` is a symlink to `CLAUDE.md`: on Windows it needs Git's `core.symlinks=true` (Developer Mode), otherwise it checks out as a one-line text file.
  - **Editing `.devcontainer/nginx/nginx.conf` needs a proxy recreate, not just a save.** It's a single-file bind mount (`docker-compose.yml`), which Docker pins to the file's *inode* — the same gotcha `docs/README.md` already documents for `docs/build/`. An editor/tool that replaces the file (rather than writing in place) leaves the running `proxy` container looking at the old, deleted inode forever; `nginx -s reload` inside it changes nothing because it's reloading that same stale content. Fix: `docker compose -f .devcontainer/docker-compose.yml up -d --force-recreate --no-deps proxy` (the `--no-deps` matters here too, same reason as `docs/README.md`'s note).
- **Non-technical work belongs in the management dashboards; the Django admin is the always-working emergency tool.**
  - **Day-to-day work goes in a dashboard.** Anything the organisation or a dojo team does as part of their normal work (running campaigns, building segments, managing events, teams, content, ...) gets a page in the matching management dashboard, to keep it user-friendly and consistent with what's already there: the dojo area (`/dojos/<id>/…`, `dojos/_admin_base.html`) for a dojo's team, the organisation area (`/manage/…`, `core/_manage_base.html`) for the organisation. Build it the same way as the existing pages: same shell and sidebar, `cd-*` styling, server-rendered forms plus htmx, access through a helper (`dojos.access`, `accounts.organisation`), 404 for anyone without access.
  - **The Django admin (`/admin/`) is for technical interventions**, and for features that don't have a dashboard page *yet*: inspecting or fixing data, a mail's full text (the dashboard's *Mail log* leaves it out: login and password mails hold working links), periodic tasks. An organisation role gets it only when asked for, 12 hours at a time (see "Organisation roles"); superusers always.
  - **The admin always stays fully usable.** Whatever breaks, it must be fixable there, so that direct database access is never needed. Never make a model read-only in the admin, never hide its fields, and never override `has_add/change/delete_permission` to block things. Let Django's permissions decide: a superuser can always do everything, and a role gets what its group grants (`accounts.organisation`). That holds even for append-only logs and rule-enforced data (belt history, the consent log, background-check decisions): say in the ModelAdmin's docstring that an edit there bypasses the normal rules, and don't block it. A feature that gets a dashboard page keeps its full admin page too. `core.tests.AdminStaysFullyUsableTests` checks that a superuser can add, change and delete every registered model; a genuine exception needs its reason in that test's `EXCEPTIONS`. **The one exception is the audit log** (`auditlog.LogEntry`, see "Audit log"): read-only, because a log anyone can edit proves nothing.
- **New features need tests.** Any new view/route, model behavior, or non-trivial function added to this repo should come with a corresponding test in the relevant app's `tests.py` (see `accounts/tests.py`, `dojos/tests.py`, etc. for the established route-test style: status codes, template used, auth/permission gating, and the actual DB effect of a POST). Don't leave a new feature untested on the assumption someone will backfill it later.
- **Keep the end-user docs current.** `docs/` (Sphinx, built with `make html-all` from inside `docs/`, which `.devcontainer/start.sh` also runs on every start — en/fr/nl, see `docs/README.md`; deps in `docs/requirements.txt`) is the help-centre content for families/volunteers/dojo teams — not this file. If a change alters a user-facing flow this documents, update the relevant `docs/source/**/*.rst` page **and** its French/Dutch translations (`docs/source/locale/{fr,nl}/LC_MESSAGES/`, see `docs/README.md` for the extract/update workflow) in the same change. It intentionally only documents flows that are actually wired up end-to-end. Pushing a `docs/` change to main publishes it to GitHub Pages ("Documentation outputs" below).
- **Keep `MAINTENANCE.md` current.** It holds the versions running in development and production with their support and end-of-life dates, the update routine, how to respond to a vulnerability (triage by whether the vulnerable code is reachable here, fix times by severity, the GDPR 72-hour breach notification) and the code-audit checks, plus a security log. When a change adds, upgrades or removes a dependency or a container image, update its row (and the *Last checked* date when you verify dates), and run `pip-audit -r requirements.txt`. **That includes every Docker image version change**: an `image:` tag in `.devcontainer/docker-compose.yml`, the workspace Dockerfile's `FROM` (`.devcontainer/dockerfile_workspace/Dockerfile`) and the MySQL/Redis `services:` in `.github/workflows/*.yml` (keep those on the devcontainer's versions): update the *Development* table (version, security-until date, status) in the same change, and record an image found past its end of life in the security log; record a new advisory in the security log with its assessment, and never upgrade on production only.
- **Keep the pages accessible (WCAG 2.2 AA).** `CODING_STANDARDS.md`, "Accessibility", has the rules (skip link and one `<main>`, headings that never skip a level, `|in_lang` for a text in another language, contrast through the tokens, 24px targets, no empty `<th>`, htmx forms that work without JavaScript). After changing a page's markup or styles, run `user-journeys/scripts/check_a11y.py` from the host (axe-core in both themes plus a 320px reflow check; exits 1 on a problem); `core.tests.AccessibilityTests` guards the structure in CI.
- **Keep the user-journey PDFs in step with the flows.** `user-journeys/` holds one PDF per persona in English, Dutch and French (an overview with screenshots for people, not the help centre; how they're made: "Documentation outputs" below). When a change touches a user-facing page or flow, run `python3 user-journeys/scripts/check_journeys.py` before finishing (plain Python and git, host or container). It compares the code behind every captured page with `user-journeys/manifest.json`, the fingerprints taken when the PDFs were made, and marks a persona **REVISIT** when that code changed substantially (a template changed by 10+ lines, two or more of its views changed, or one is gone). For a flagged persona, look at whether what it sees or does actually changed (a step added, removed or reordered, a page redesigned, options added to a captured page): if so, regenerate that persona's PDFs in all three languages and rerun `manifest.py`; if not (a refactor, a wording fix), only rerun `manifest.py` to take a new baseline. Commit the new `manifest.json` with the change. When you can't regenerate in that session, say in your summary which PDFs are now stale rather than skipping it silently. "Minor changes" needs no action.

## Commands

Run everything inside `.devcontainer/` (nginx + TLS on `coolregistration.localhost`, containerized MySQL, Redis, Mailpit, two Celery workers with beat embedded in one) — see the workflow rule above. `website/settings.py` reads `DB_*`/`REDIS_*`/`EMAIL_*`/`COOKIE_DOMAIN` env vars with host-friendly defaults (so a host-level run isn't *broken*, just not what this repo's workflow expects — Redis/Channels behavior in particular can diverge, see above); `.devcontainer/docker-compose.yml` sets the real ones.

```sh
docker compose -f .devcontainer/docker-compose.yml up -d          # db, redis, proxy, workspace — check first with `docker ps`
docker compose -f .devcontainer/docker-compose.yml exec workspace bash    # a shell inside the workspace container
```

**Only port 443 is published** (the `proxy` service, `https://coolregistration.localhost`); no other container has a host port, not even 80 (so type `https://`). VS Code doesn't forward ports either (`otherPortsAttributes` in `devcontainer.json` ignores auto-forwarding: runserver's `localhost:8000` would skip nginx), and `start.sh` prints every address just before the dev server starts. Every tool is a path behind nginx (`.devcontainer/nginx/nginx.conf`): `/docs/`, `/mails/` (Mailpit), `/phpmyadmin/` (`PMA_ABSOLUTE_URI` matches it; it logs in by itself as the app's database user, `PMA_USER`/`PMA_PASSWORD`) and `/otp/` (the testers' authenticator, below). **When the site can't answer** (a 503 from the per-worker cap, a 502 while it's down or restarting, a 504), nginx shows our own page, `.devcontainer/nginx/errors/busy.html` (`error_page` with `proxy_intercept_errors` on the Django locations only; `/health/` and `/api/` keep their own answers, and so do Django's 404 and 500 pages): self-contained on purpose (inline styles and logo, no script, only the site's fonts from `/static/`, guarded by `pages.tests.ProxyErrorPageTests`), in nl/fr/en, the example for production's proxy (`CAPACITY.md`). A new dev tool gets a path there too, never a port (and a subdirectory setting of its own if it builds absolute links), proxied through a variable (`set $tool tool:port; proxy_pass http://$tool;`, plus a `rewrite` to strip the prefix if it serves from its root): nginx then looks the container up per request through Docker's DNS (`resolver 127.0.0.11`), so a container that's missing or recreated is a 502 on its own path, never an nginx that won't start (`host not found in upstream`). Inside the stack, containers reach each other by service name (`db:3306`, `mailpit:1025`, `workspace:8000`, `otp:8000`). **Prometheus and Grafana** (behind a flag: the `monitoring` Compose profile, off by default) scrape `/metrics/` from `workspace:8000` with the dev-only `METRICS_TOKEN` (`dev-metrics-token`, set on the `workspace` service; `workspace` is in its `ALLOWED_HOSTS` for that) and serve at `/prometheus/` and `/grafana/` (no login: anonymous Grafana admin, the data source and the *CoderDojo site* dashboard provisioned from `.devcontainer/monitoring/`; edit the dashboard's JSON there to keep a change). Turn them on with `COMPOSE_PROFILES=monitoring` in the environment that runs `docker compose` or in `.devcontainer/.env` (a VS Code rebuild reads it), or once from the host with `docker compose -f .devcontainer/docker-compose.yml --profile monitoring up -d`; while off, nginx answers 503 on both paths with that hint. **The testers' authenticator** is 2FAuth (`otp` service, volume `otp-data`) at `/otp/`: the current code of every account with an authenticator app, filled from the data by `manage.py seed_otp_vault` (end of `start.sh`; rerun it after someone's app changes; it syncs only its own entries, service `CoderDojo (dev)`, and does nothing without `OTP_VAULT_URL`, which only the devcontainer sets). There's no 2FAuth login: nginx signs everyone in as one shared user with a `Remote-User` header (its reverse-proxy guard), which the command sends too.

From that shell (or prefix any of these with `docker compose -f .devcontainer/docker-compose.yml exec workspace`):

```sh
# Dev server — reachable via https://coolregistration.localhost through nginx
python manage.py runserver 0.0.0.0:8000

# Migrations
python manage.py makemigrations <app>
python manage.py migrate

# Tests (plain Django test runner — no pytest config in this repo). They use their own Redis
# cache database (db 3, see CACHES in settings.py), so a test run never touches the dev server's cache.
python manage.py test                    # all apps
python manage.py test accounts           # one app
python manage.py test accounts.tests.SomeTestCase.test_something   # one test
# If the debug toolbar's E001 check refuses to run tests, add --debug-mode
# (keeps DEBUG=True for the run) rather than working around it in settings.
python manage.py test --debug-mode
# No --parallel: cloning the test database needs mysqldump, which the workspace
# image doesn't have. A run that was interrupted leaves test_<DB_NAME> behind;
# --noinput drops it without asking.

# Django shell / admin superuser
python manage.py shell
python manage.py createsuperuser

# Translations (en-us, nl-be, fr-be; the full makemessages command with its
# --ignore flags and the workflow are under "i18n" below)
python manage.py makemessages -l nl_BE -l fr_BE --ignore=".venv/*" --ignore="docs/*" --ignore="staticfiles/*" --ignore="media/*"
python manage.py compilemessages -l nl_BE -l fr_BE --ignore=".venv/*"
```

**Running without DEBUG (to check speed):** `DEBUG` on the `workspace` service is `${DEBUG:-true}`, so `DEBUG=false` in the environment that runs `docker compose` (or in `.devcontainer/.env`) runs the site like production. `start.sh` then collects the static files into `staticfiles/` (`STATIC_ROOT`, set only in the devcontainer) and serves the site with production's command, `gunicorn -k uvicorn.workers.UvicornWorker main:app` (gunicorn and uvicorn are in `requirements-dev.txt`; `WEB_CONCURRENCY=<n>` for more workers) instead of `runserver`: no autoreload, no debug toolbar, Django's plain error pages. With DEBUG on it empties `staticfiles/`. nginx serves `/static/` from `staticfiles/` when the file is there and otherwise passes it to Django (so with DEBUG on you always get the file you're editing), and serves `/media/` from disk in both modes. It gzips text responses (pages, CSS, JS, JSON, SVG) in both modes too. The switch needs the `workspace` container recreated and `start.sh` run again; the stack is usually VS Code's (compose project `coderdojo-event-registration_devcontainer`), so a rebuild from VS Code is the easy way. `totp_code` and `simulate_bounce` are DEBUG-only; use `/otp/` (or the `totp_secret` column in an authenticator app) meanwhile.

Claude Code's login/settings/session history in the `workspace` container live on the `claude-config` named volume (mounted at `/root/.claude`, with `CLAUDE_CONFIG_DIR` pointing there so `.claude.json` is inside it too) — a rebuild keeps them; only `docker compose ... down -v` wipes them (along with the DB volume).

The local dev TLS CA/cert for `coolregistration.localhost` is created by `start.sh` when missing (the server cert also when it nears expiry; the CA never gets replaced, since the host trusts it); details and the manual steps in `.devcontainer/certs/README.md`.

**Requirements are split:** `requirements.txt` holds only the **production runtime** dependencies (what the running site imports, plus their pinned transitive deps; `scripts/deploy.sh` installs this on the server). `requirements-dev.txt` includes it via `-r` and adds ruff, the data-loading stack used only by the `import_*` commands (`geopandas`, `pandas`, `shapely`, `bs4`, ...; imported *inside* those commands, never at module level). The devcontainer image installs `requirements-dev.txt`. A new package the site imports at runtime goes in `requirements.txt`; anything only needed locally goes in `requirements-dev.txt`.

**Profiling with django-silk (development only):** silk is in `requirements-dev.txt`, never installed in production. `settings.SILK_ENABLED` is on while `DEBUG` is and the package is installed (`SILK=false` switches it off, `SILK=true` on with DEBUG off, to profile the production-like run; set it like `DEBUG`, in the environment that runs `docker compose` or `.devcontainer/.env`, then recreate the `workspace` container); only then are its app, middleware and `/silk/` pages there (staff logins only: it stores whole requests, posted passwords included; `privacy/privacy.py` classifies its models). **Never import silk in the site's code**: annotate with `core.profiling.profile` (`@profile()` or `with profile(name=...)`), which is silk's `silk_profile` when silk is on and does nothing otherwise. Clear what it recorded with `manage.py silk_clear_request_log`.

Lint/format — `ruff` (config in `pyproject.toml`; tool itself in `requirements-dev.txt`, not `requirements.txt`):

```sh
pip install -r requirements-dev.txt
ruff check .              # lint
ruff format .             # format
mypy                      # types: the modules in pyproject.toml's [tool.mypy] files
```

**Type checking is gradual** (`CODING_STANDARDS.md`, "Type checking"): mypy with django-stubs' plugin checks only the modules listed in `[tool.mypy] files`, which are fully annotated (the service modules first). A service module you annotate joins the list; new service code is written annotated; views, forms and tests stay as they are. A type-only import goes under `TYPE_CHECKING`.

The devcontainer's `db` service auto-grants its app user rights on Django's `test_<DB_NAME>` database via `.devcontainer/db-init/01-grant-test-db.sql` (runs once, on a fresh volume, via MySQL's `docker-entrypoint-initdb.d`), so `manage.py test` works there with no setup. ## Architecture

### Apps and what owns what

Mermaid diagrams of the whole data model (entities, role/access rules, event and background-check state machines) live in `DATA_MODEL.md` — update the relevant diagram when you change a model or one of those flows. **The data-model redesign has landed** (all eight phases; `DATA_MODEL.md` §10 keeps its rationale, implementation decisions and plan; e.g. one `User` table with `account_type` instead of role subclasses; which also fixes the **nomenclature**: **Champion** = the dojo owner, **Mentor/Coach** = an adult helper, **Ninja** = a child aged 7–17 visiting a dojo, **Youth mentor** = a ninja helping run events, **Badge** = an award, one-off or a count-based milestone such as the attendance wristbands, **Belt** = a ninja's proficiency level, separate from milestones (a milestone badge can optionally grant a belt), stored as an append-only belt history (current level = the highest belt, `Ninja.current_belt`; it's the only record of a ninja's coding level — there's no separate experience-level field), shown on the ninja's account page, the family page's child cards and in the management tooling (attendance rows, the ninja admin list), awarded only by accounts that actively manage a dojo (an active champion/mentor membership, recorded along with the account; organisation accounts can only view belts), and not linked to pathways yet). Use these names in code and UI. The model:
- **Accounts:** two account types, a normal account (background-checked only to become a champion or mentor) and a ninja account. Champion, mentor and youth mentor are roles on a User↔Dojo membership, replacing the `Mentor` table and the `DojoOwner`/`HelperAccount`/`Guardian` subclasses.
- **Joining:** mentor/champion approval is one-time and account-level. Joining a dojo is then a request the dojo's team accepts (or they add you). Memberships go `requested → active → dormant`, with dormant ones kept for past event teams.
- **Dojo lifecycle:** `draft → active ⇄ dormant → archived → draft`. The champion launches without approval. Dormant and archived both require no active events and auto-decline pending join requests. Dormancy is always manual, prompted after six months with no events by a dashboard flag and a persistent team/board notification. Hidden dojos stay in ninjas' history.
- **Champion role:** moves only by transfer to an active mentor. Any active mentor can accept join requests, add mentors and promote youth mentors.
- **Profiles:** the team-page profile is on the account, shared across dojos. `ORGANISATION_TEAM_MEMBER` is a display-only listing with a position (e.g. "Member of the board"), separate from management-dashboard access (`ORGANISATION_ROLE`).
- **Pathways:** optional many-to-many links at dojo → event → registration, each pre-filled from the level above.
- **No data migration:** the database only holds seeded test data, so the redesign's migrations were reset to a fresh initial set per app (an older dev database has to be recreated — see `DATA_MODEL.md` §10 "No data migration", including how to reset only the database without `down -v` wiping the `claude-config` volume). Seeders: `seed_champions`, `seed_mentors`, `seed_guardians`, `seed_events`, `seed_applications`, `seed_ninja_history`, `seed_upcoming_registrations` (children signed up for upcoming sessions at their home dojo and nearby dojos, and three sessions filled to test the waiting list: full with children waiting, exactly full, one place left; no mail; `seed_credentials.csv` names the parents with a child waiting), `seed_two_step` (two-step login for one seeded organisation admin, champion, mentor and parent; fresh databases only), `seed_login_links` (a seeded parent and mentor that log in with an emailed link, never the `seed_two_step` picks; fresh databases only; their `seed_credentials.csv` password column says `(login link)`), `seed_faqs`, `seed_testimonials`, `seed_announcements` (random updates for dojos that have none; order in `.devcontainer/start.sh`), `seed_organisation` (the organisation dojo, its two events and a promotion per placement), `seed_mailing` (example email templates and draft campaigns; no dates, so `start.sh` runs it on every start) and `seed_content_languages` (every start too: dojo languages by region and the Dutch/French versions of all seeded texts from `pages/seed_translations.py`; it only touches rows still on their English seed text, so seeders must find their rows by something other than a translatable text, e.g. dojo + position or start time); keep them rerun-safe — a choice made only when a row is new must use its own RNG, not the command's shared one. Seeded logins go to `seed_credentials.csv` (gitignored) through `accounts.seed_credentials.write_credentials`, which merges by username (its `totp_secret` column holds an account's authenticator-app key, filled from the data); `manage.py describe_seed_accounts` (end of `start.sh`) writes each login's description column from the data (what a tester can do with it) and, with DEBUG on, gives seeded logins missing from the file a new password.
**Organisation-run events** (CoderDojo Girlz, Coolest Projects) live on an **organisation dojo** (`Dojo.kind = organisation`, `DATA_MODEL.md` §12): a normal dojo with a team, admin area and background-check rule, but never listed (`Dojo.objects.public()`/`is_public` exclude it; its event pages say "Organised by", `events/partials/_organiser.html`). Only its events can set `Event.external_registration_url` (the page links out, `event_signup` redirects, no registrations here). New code that lists or picks dojos should go through `public()`, or exclude `kind=organisation` explicitly. **Promoting events** is `content.Promotion` (an event, a `placement` of four, `rank`, a `starts_at`/`ends_at` window): always read it through `Promotion.objects.showing(placement)`, managed on the organisation dashboard (`/manage/promotions/`, `content/manage.py`).
Keep routing role checks through `dojos.access`, team changes through `dojos.team`, onboarding through `applications.services`, badges/belts through `events.awards`, and signing up for a session and cancelling a place through `events.registrations` (`sign_up`, `cancel`; `RegistrationError`), which locks the session's row so simultaneous sign-ups can't overbook or repeat a waiting-list position (`events.tests.BookingConcurrencyTests`, real threads in a `TransactionTestCase`; `CAPACITY.md`, finding 1): never create, delete or confirm a `Registration` elsewhere.

Linked (redesign phase 4) at three optional M2M levels, each pre-filled from the one above but never restricted to it: `Dojo.pathways` (Settings page) → `Event.pathways` (`EventForm` pre-selects the dojo's on a new event) → `Registration.pathways` (copied from the event at `event_signup`, narrowed per row on the attendance list via `dojo_event_registration_pathways`).

It never imports `campaigns`: what it needs from there is registered with it (`mailing.template_users`). See "Background jobs" and "Mailing and segmentation" below.

Its Celery tasks keep their old registered names (`name="mailing.tasks.…"`), which the beat schedule uses.

The organisation's contact details live in `settings.ORGANISATION_CONTACT`, exposed to every template as `organisation` by `core.context_processors`.
- **`pages`** — the site as visitors and the organisation meet it, assembled from the other apps (nothing imports it): the homepage (`pages/views.py`), the Contact and Code of conduct pages (`/contact/`, `/code-of-conduct/`), `/manage/`'s landing (`pages/manage.py`), the audit log page, `/health/`, the Django admin site (`pages.admin_apps.AdminConfig`) and the content seeders' translations (`pages/seed_translations.py`, `seed_content_languages`). The management switcher's contexts are `accounts/manage_nav.py` (its tags `accounts/templatetags/manage_nav.py`; the organisation bell's tag `notifications/templatetags/notification_bells.py`).
- **`privacy`** — the GDPR classification of every field of every model (`core/privacy_registry.py`; each app declares its models in its own `privacy.py`) the art. 30 register built from it (`manage.py privacy_register`) and a person's data export (`privacy/export.py`, the family's `/account/data/` and the organisation dashboard's `/manage/privacy/`). See "Privacy" below.
- **`api`** — the API for apps that work for a dojo (`/api/v1/`, django-ninja; see "API" below): the dojo's API clients (`DojoApiClient`, OAuth 2.0 client credentials through django-oauth-toolkit), their page in the dojo admin area, and the attendance endpoints.
- **`monitoring`** — the site's measurements of itself (`/metrics/`, the daily `CapacitySample`, the capacity model and `seed_scale`/`capacity_report`; see "Capacity and monitoring" under "Deploying").
- **`website`** — settings/urls/asgi and the Celery app (`website/celery.py`).

**The apps are layered** (`CODING_STANDARDS.md`, "Layers"; `[tool.importlinter]` in `pyproject.toml`, checked by `lint-imports` locally and in the Code audit workflow): `pages` > `api`, `campaigns`, `privacy` (what reads across the domain) > the domain (`accounts`, `applications`, `content`, `dojos`, `events`, `mailing`, `notifications`, `pathways`, which may use each other) > `core`, `geo`, `monitoring` (the foundation, which knows no app). An app imports its own layer and the ones below, never one above; tests, test helpers and management commands may reach anywhere. When a lower layer needs something from a higher one, the higher one registers it from its `AppConfig.ready()` (the image library's folders, `/metrics/`' mail queue via `monitoring.collect.register_source`, `mailing.template_users`), instead of the lower one importing it. A new app picks its layer and gets a line in the contract.

Each app with URLs owns its own `urls.py`, included from `website/urls.py` with an empty prefix (`path("", include("dojos.urls"))` etc.) — routes live at the top level, not namespaced under `/dojos/`, `/events/`, etc.

### Account model

`accounts.User` (`AUTH_USER_MODEL`) is every login; `User.account_type` is `adult` or `ninja` (a ninja's own login — `user.is_ninja`). **Parents aren't a role or subclass any more** (redesign phase 1, `DATA_MODEL.md` §10): any adult account is linked to its children through `accounts.Guardianship` (a child can have several guardians), and `Ninja.objects.of_guardian(user)` is how to get "this account's children" — never filter on a guardian FK on `Ninja` (there isn't one). Family pages live under `/account/` with no id in the URL (`account_home`, `edit_account`, `change_email`, `ninja_detail`, `edit_ninja`, `ninja_badges`, `add_ninja`, `ninja_login_create`/`_resend`/`_remove`/`_two_step_off`/`_use_password`/`_email`, `cancel_registration`), always scoped to `request.user`; `accounts.views._get_own_ninja` 404s (not 403s) for a ninja the account isn't a guardian of, and with `allow_self=True` also lets a ninja's own login view (never edit) its own page; the one thing that login changes itself is its avatar (`ninja_avatar`, `accounts.forms.ChildAvatarForm`: the standard avatars only, linked from the image library, never an upload). The account holder's own details (name, phone, postcode) are edited in place at the top of the account page, the same htmx click-to-edit as a child's header (`edit_account`, `accounts.forms.EditAccountForm`, partials `_account_details_display.html`/`_account_details_edit.html`; without JavaScript it renders the whole account page with the form open). The email address is shown there but never edited in place: **changing it is its own confirmed flow** (`DATA_MODEL.md` §22), always through `accounts/email_change.py` (`request_change`, `read_token`, `confirm_change`; `EmailChangeError`): the family asks on `/account/email/` with its password (or an organisation admin starts it on `/manage/privacy/<id>/email/`, `privacy.views.manage_privacy_email`, for a family that lost its old mailbox, or a guardian for their child's own login, `ninja_login_email` → `child_accounts.change_email`; the link records who started it and as what, `started_as`, and a guardian's is checked again on confirming, `DATA_MODEL.md` §24), a signed link (24 hours, single use: it carries a fingerprint of the current address) goes to the new address (`email_change_confirm`), and `confirm_email_change` (GET asks, POST changes) saves it and queues `email_changed` to the old address. The family's link needs that account logged in; one the organisation or a guardian started works logged out and then offers a password reset (or a login link, for an account on one). `User._get_session_auth_hash` covers the email as well as the password, so a new address (from anywhere, the Django admin too) ends the account's other sessions; the confirming session keeps itself with `update_session_auth_hash`.

There are **no role subclasses of `User` any more**: being a champion or mentor is an approved `applications.Application` plus a valid background check on the account (redesign phase 3), and what they do at a dojo is a membership (below). `accounts.context_processors.user_roles` exposes `user_is_approved_champion` / `user_is_approved_mentor` / `user_applied_champion` / `user_applied_mentor` / `user_admin_dojo` / `user_has_organisation_role` / `user_is_organisation_admin` / `user_can_manage` (the nav's *Manage* link, also for every organisation role: the board reaches its Django admin request page through it) to every template. There's no multi-table inheritance left anywhere: badges are one `events.Badge` table with a `kind` (`one_off` / `milestone`).

`accounts.Ninja` (a child aged 7–17; formerly `Participant`; `name` is the first name, plus `family_name`, and `full_name` joins them: show `full_name` wherever the dojo team sees a child or a child is picked from a list, the first name in the family's own sentences) is a plain model, *not* a User — a ninja only gets a login (a `User` with `account_type="ninja"`, linked via `Ninja.account`) if a parent opts them in; most don't have one. Registrations, badges and belts link to it as `ninja`. **A ninja's own login is the guardian's to give and take away** (`DATA_MODEL.md` §17): always through `accounts/child_accounts.py` (`give_login` with the child's own email and a login method → a ninja `User` with no usable password plus the `ninja_account_created` mail, with a set-password link or the first login link; `turn_off_two_step`, `switch_to_password` and `change_email` for the guardian's actions on the *Own login* card, each confirmed with the guardian's own `ConfirmIdentityForm`; `remove_login` deletes it, or disables it (`is_active=False`) and ends its memberships when it was ever on a dojo team, since `Event.team` points at memberships). The guardian keeps editing the child's details either way. A ninja's login signs itself up for sessions and cancels its own places: event sign-up lists `Ninja.objects.signable_by(user)` (an adult's children, or the ninja itself), never `of_guardian` directly. **A ninja's home dojo** (`Ninja.home_dojo`, `member_since`) follows `accounts/home_dojo.py` (`DATA_MODEL.md` §18): set at the child's first sign-up from that session's dojo (never an organisation dojo), then only the guardian changes it (child edit form); never moved automatically, never by the dojo team. The 7–17 rule (`accounts.models.ninja_birth_date_error`) applies whenever a date of birth is entered or changed — `Ninja.clean()` and the family forms check it; it's never retroactive, so a ninja who has turned 18 stays editable.

**Dojo teams are memberships** (redesign phase 2): `dojos.DojoMembership` is one account's place on one dojo's team — `role` (`champion` = the dojo's owner, exactly one active per dojo; `mentor`; `youth_mentor` = a ninja account, `promoted_by` a champion/mentor of the same dojo) and `status` (`requested` → `active` → `dormant`, unique per account+dojo; leaving goes `dormant`, never deleted, so `Event.team` keeps its history, and rejoining reuses the row). There is no `Dojo.owner` and no `Mentor` table any more — `dojo.champion` / `dojo.champion_membership` give the owner, `dojo.memberships.managers()` the active champion+mentors, `for_team_page()` the public listing (champion first). The team-page profile (`display_name`/`title`/`bio`/`photo`/`show_on_team_pages`, `user.team_name`) lives on `accounts.User` and is shared by every dojo the person is on; `DojoMembership` exposes it (`.name`, `.photo`, ...) so the shared `_mentor_avatar.html` partial works for memberships and `content.OrganisationTeamMember` (the organisation's display-only team listing, with a `position`) alike. **Every team/lifecycle change goes through `dojos/team.py`** (`request_to_join`, `accept_request`, `add_mentor`, `promote_youth_mentor`, `leave`, `transfer_champion`, `change_status`, `notify_managers`, ...), which enforces the rules and raises `TeamError` with a user-facing message — don't edit memberships or `Dojo.status` directly from views. `Dojo.status` is `draft` (model default) → `active` ⇄ `dormant` → `archived` → `draft`; only `active` dojos are public (`Dojo.objects.public()`, and `Event.objects.visible()` also requires `dojo__status=active`); going dormant/archived needs no upcoming draft/open events and auto-declines pending requests; saving the dojo clears the public caches (below). Tests: use `dojos.testing.make_dojo(name, champion=..., status=ACTIVE)` / `add_member(...)` rather than `Dojo.objects.create` (which gives a hidden draft).

**Organisation roles** (redesign phase 6): `accounts.OrganisationRole` (`board` = read-only oversight + the organisation's team listing, `admin` = also edits dojos/events/content/catalogues and runs mail campaigns) is access to the management side: the organisation dashboard (`/manage/`) for what has a page there, and the Django admin for everything else and for emergencies. `accounts/organisation.py` maps each role to a permission group and syncs the groups via signals — grant/revoke the role, never set those by hand. **A role never opens the Django admin by itself** (`DATA_MODEL.md` §23): its holder asks for it on `/manage/django-admin/` with a reason and their password, for `ADMIN_ACCESS_HOURS` = 12 (`accounts.AdminAccessGrant`, always through `accounts/admin_access.py`: `request_access`, `end`, `end_for`, `close_expired`; `AdminAccessError`). `is_staff` follows the grants (`sync_staff`: on while one is open, or for a superuser), `pages.admin_site.AdminSite.has_permission` checks for an open grant on every request, the beat job `accounts.tasks.close_admin_access` (every 5 min, `periodic`) records the end, and losing the last role ends it. Every request notifies the other organisation admins; grants are in the audit log. **Superusers are never time-boxed and never made on the site**: that's a technical intervention on the server (`createsuperuser`). Tests open access with `accounts.testing.with_admin_access(user)`. **Who holds which role is managed on the People pages** (`/manage/people/`, `accounts/people.py`, the `people` area), always through `accounts/organisation_people.py` (`set_roles`, `end_access`; `OrganisationPeopleError`: never your own roles, always one admin left, only active adults; mails `organisation_role_changed`), and someone without an account is invited through `accounts/invitations.py` (`invite`, `resend`, `withdraw`, `accept`; `accounts.OrganisationInvitation`, token stored hashed, 14 days, granted only to an account with the invited address, removed 30 days after it ended by the retention job). A third role, `reviewer`, reviews background checks and decides applications (the organisation dashboard's *Volunteers* pages, `DATA_MODEL.md` §21; `is_reviewer`, which also counts the permission granted by hand); only it holds `applications.can_review_background_checks`. **Which dashboard pages a role opens is by area** (`DATA_MODEL.md` §23): each group of the organisation sidebar is an `accounts.organisation.Area` with a permission (`AREA_PERMISSIONS`: `accounts.manage_communication`, `manage_public_site`, `manage_ninjas`, `manage_privacy`, `manage_security` on `OrganisationRole`, and Volunteers = the review permission, Audit log = `auditlog.view_logentry`), given to the roles through `ROLE_PERMISSIONS` (`admin` all but Volunteers, `reviewer` Volunteers, `board` none). Every organisation view calls `require_area(request, Area.X)` (404 without it, or below the sign-in policy); the sidebar (`contexts.can.<area>`), `/manage/`'s landing (`pages.manage.AREA_LANDINGS`, the first area) and the nav's *Manage* link follow `areas_of(user)`. It's `has_perm`, so a permission granted by hand counts and a superuser opens every area. A new organisation page picks its area; a new sidebar group gets a new area (a permission, an `AREA_PERMISSIONS` entry, a landing). `is_organisation_admin` is the role itself, not page access. No role can award belts. Admin actions that change data should declare `permissions=["change"]`, or view-only roles can run them.

Every account is created by its own holder (family sign-up, the sign-up without children for someone who wants to start a dojo or volunteer, `register_individual`, or the sign-up behind an organisation invitation, `organisation_invitation_sign_up`) — there are no admin-provisioned logins or emailed temporary passwords any more. `accounts.middleware.ForcePasswordChangeMiddleware` still redirects any account with `must_change_password` set (e.g. by an admin after a reset) to the password-change form. `accounts.backends.EmailOrUsernameBackend` lets login accept either email or username.

Family sign-up is self-service (`accounts.views.register_guardian`, `RegisterGuardianForm`; a logged-in account is redirected to its account page instead) — no admin approval or background check, since a parent only ever manages their own children (unlike champions and mentors, who work directly with other people's kids and need the background check). It creates a plain adult `User` plus a `Guardianship` per child, in one transaction (with a password, or on a login link: then it doesn't log in but mails the first login link, which confirms the address, `DATA_MODEL.md` §24), plus, if ticked, the guardian's consent to the children's details choosing which mail they get (an optional checkbox with the approved wording `accounts/partials/_child_data_consent.html`, `accounts.consent`; *Add a child* has it too, and Mail preferences a switch per child; it only matters to segments, never to signing up); the username comes from `accounts.provisioning.unique_username()`. Both public sign-ups (`register_guardian`, and `register_individual` with `RegisterIndividualForm`: the same details minus the children) honour a safe `next` (`accounts.views.signup._signup_next`, kept in a hidden field and carried in the first login link), so a visitor stopped by `event_signup`'s login wall who picks *Create an account* (the login page and the *Get involved* chooser pass `next` on) lands back on that session's sign-up. The child rows on that form are `accounts.forms.ChildRowsFormSet` (prefix `child`, one `SignUpChildForm` per row): the page clones the formset's `empty_form` for "Add another child", and since "Remove" leaves gaps in the numbering, the formset's rows are the numbers the post actually has (each one required, at least one).

### Two-step login and the sign-in policy

`DATA_MODEL.md` §15 has the design. Any person's account (an adult's, or a ninja's own login: the same options for every login, §24) can turn on two-step login on its *Sign-in security* page (`/account/security/`, `accounts/security_views.py`): an authenticator app (at most one), passkeys and ten backup codes, all django-otp devices (django-two-factor-auth 1.18.1 on django-otp; it officially stops at Django 5.2, we run and test it on 6.1). **Every change to an account's methods goes through `accounts/two_step.py`** (`add_app`, `add_passkey`, `remove`, `turn_off`, `make_backup_codes`; `TwoStepError`), which keeps exactly one method named `default` (what the package's login asks for first) and sends the security mails (`two_step_*`, `backup_code_used`). **`/login/` (`accounts.views.LoginView`, a django-two-factor-auth `LoginView` subclass: password, then code/passkey/backup code) is the only way to log in**: another route would skip the second step, and the Django admin's login is patched to redirect there. The one other door, a login link (`/login/link/<uidb64>/<token>/`, `accounts.views.LoginLinkView`), is that same `LoginView` with a different first step, so the second step still follows.

**Password or login link** (`DATA_MODEL.md` §24): each account chooses, `User.login_method` (`password`, or `link` and then no usable password); the organisation never sets it. Everything about it goes through `accounts/login_links.py` (tokens in the style of Django's password reset over the password hash, last login, email and method, so single use and 15 minutes, the first one after sign-up 3 days; `request_link`, which answers the same whatever the address; `request_switch_to_link` → confirmed from the mailbox → `switch_to_link`; `switch_to_password`; `LoginLinkError`). Forgot password sends a link account its login link. **Anything that asks for the password to confirm a change uses `accounts.forms.ConfirmIdentityForm`** (`request=`, rendered with `accounts/partials/_confirm_identity.html`): for an account without a password a login in the last 10 minutes counts (`accounts/reauth.py`, recorded on every login), otherwise it offers a login link back to the page (`login_link_reauth`). The security mails go through `accounts/security_mail.py`, which also tells a child's guardians (`child_login_changed`). Passkeys are checked against `SITE_URL`, not the request (`accounts/webauthn_entities.py`, since TLS ends at the proxy); their browser side is `CoderDojo.initPasskey` in `bundle.js`.

**Which roles must use it** is the organisation's policy, `accounts.SignInRequirement` (a `level` per role, `password` < `two_step` < `passkey`, from `required_from`), set on `/manage/security/` (`accounts/manage.py`, which also turns off someone's two-step login when they lost their phone). Today every role is on `password`, so it's optional for everyone. `accounts/sign_in.py` works out an account's requirement (the strongest among its roles; a later one is only a notice, `sign_in_notice` in the page shells) and whether a request meets it. `SignInRequirementMiddleware` sends an account without the device to set it up, and logs out a session that skipped the second step; the lock itself is in `dojos.access.require_dojo_access`, `accounts.organisation.require_area`, the Django admin (`pages.admin_site.AdminSite`, installed as `admin.site` through `pages.admin_apps.AdminConfig` in `INSTALLED_APPS`) and the notification consumer. A new area a role opens checks `accounts.sign_in.meets_requirement(request)` the same way. Ninja logins and service accounts are never asked. Tests: `core.testing.login_data`/`token_data` post the login's steps, `login_verified(client, user)` logs in with a verified session; seeded accounts with two-step login come from `seed_two_step`, with the app key in `seed_credentials.csv`'s `totp_secret` column, `manage.py totp_code <username>` for the current code, and every code at `/otp/` in the devcontainer (`seed_otp_vault`).

### One management area: the organisation and its dojos

`DATA_MODEL.md` §20. The organisation's dashboard (`/manage/…`, `core/_manage_base.html`) and a dojo's admin area (`/dojos/<id>/…`, `dojos/_admin_base.html`) are one management area: both bases extend `core/_manage_shell.html` (head, sidebar frame, top bar, messages, sign-in notice) and only fill their sidebar menus, keeping their own block names (`manage_*`, `admin_*`). ### Live notifications: Django Channels over Redis

The admin sidebar's notification bell (`dojos/templates/dojos/partials/_notification_bell.html`) is backed by `notifications.Notification` — `recipient` + `read` live on the same row, so per-user read state falls out for free; `dojo` (nullable FK) is what the admin panel of someone on several dojos' teams filters on, via `dojos.views._notification_context`. A dojo-level event that concerns more than one person fans out to one row per recipient sharing the same `dojo`/`text`/`url`, each independently read/unread.

**The organisation dashboard has its own bell** (`DATA_MODEL.md` §23): notifications created with `notify(..., organisation=True)` (`Notification.organisation`; a plain `dojo=None` is a personal notice, not the organisation's), shown by `{% organisation_bell %}` in `core/_manage_base.html`, with their own views in `notifications/views.py` and a live consumer, `notifications.consumers.OrganisationNotificationConsumer` at `/ws/manage/notifications/` (same per-user group as the dojo consumer; open to the Organisation context, `accounts.manage_nav.require_organisation_context`). The same partial, `_notification_bell.html`, serves both bells: without a `dojo` its links go to the organisation views.

**Creating a notification**: always through `notifications.services.notify(recipient, text, url="", dojo=None, params=None, organisation=False)` — never `Notification.objects.create()` directly. `text` is a `gettext_lazy` message with its `params`, rendered in the recipient's language (see "i18n"). It creates the row (the source of truth) and then best-effort nudges that recipient's live connection via the channel layer; a channel-layer failure is swallowed, same fail-open spirit as `CACHES`' `IGNORE_EXCEPTIONS`. Dojo-level events notify the dojo's managers through `dojos.team.notify_managers(dojo, text, url)` (one row per active champion/mentor, never youth mentors): a mentor application against a specific dojo (`applications.views.register_helper`), a waitlist promotion (`accounts.views.cancel_registration`) and a join request; individual team changes (accepted, added, declined, champion handed over) notify the person concerned via `notify` directly.

**Live push is WebSockets via Django Channels**, not SSE/polling — `daphne` (top of `INSTALLED_APPS`, so `manage.py runserver` transparently serves ASGI instead of WSGI), `ASGI_APPLICATION`/`CHANNEL_LAYERS` in `website/settings.py` (the latter is `channels_redis`, same `REDIS_HOST`/`REDIS_PORT` as `CACHES` but db 1, not 0, with a `socket_timeout` longer than channels_redis's 5-second blocking read: redis-py 8's default of 5 seconds closed every socket a few seconds after it opened, `notifications.tests.ChannelLayerSettingsTests`), and `website/asgi.py`'s `ProtocolTypeRouter` (http → normal Django, websocket → `notifications.routing.websocket_urlpatterns` behind `AllowedHostsOriginValidator(AuthMiddlewareStack(...))`, so `scope["user"]` is the same session-authenticated user a normal request would see). `notifications.consumers.NotificationConsumer` checks admin access (an active champion or mentor, `dojos.access.dojo_role`) once at `connect()` (closes the socket on a mismatch, same 404-not-403 reasoning as `dojos.access.require_dojo_access`) and, on every group event, re-renders `_notification_bell.html` fresh from the DB and pushes it as one `hx-swap-oob="true"`-wrapped fragment — `htmx-ext-ws` (loaded in `_admin_base.html`) does the DOM swap from that alone, no client-side JSON handling. The bell's own `ws-connect` lives on a separate, never-swapped `<div>` in `_admin_base.html` specifically so the bell's own oob updates (and `mark_all_notifications_read`'s htmx response, which reuses the identical oob-id-matching trick) never tear down the socket that's delivering them.

If you add a Channels consumer that touches the database, test it with `TransactionTestCase`, not `TestCase` — the consumer's DB access runs on a separate thread (`channels.db.database_sync_to_async`) with its own connection, which a `TestCase`'s wrapping transaction (held on the main thread's connection) is invisible to. `notifications.tests`/`dojos.tests.NotificationConsumerTests` are the reference examples, including `@override_settings(CHANNEL_LAYERS=...InMemoryChannelLayer...)` so consumer tests don't need a real Redis.

`django-debug-toolbar`'s `CachePanel` and `TemplatesPanel` are disabled (`DEBUG_TOOLBAR_PANELS` in `website/settings.py`, dev-only either way) — both do unsafe lazy model stringification while serializing call/context args for display (cache-call args for `CachePanel`; every template context value for `TemplatesPanel` — any model whose `__str__` queries related rows), which is merely wasteful under WSGI but hard-errors every single page it touches (`SynchronousOnlyOperation`) now that requests are served over ASGI. Any other panel that stringifies arbitrary model instances is a candidate for the same bug if it starts erroring — these two are just the ones actually hit so far.

**A model's `__str__` never queries**, for the same reason: under ASGI, a lazy foreign-key lookup inside `__str__` raises `SynchronousOnlyOperation` wherever something stringifies a row from an async context. So a model whose `__str__` names a related object preloads it in its default manager, the plain Django way: a `Manager` subclass whose `get_queryset()` adds `select_related(...)` (built with `Manager.from_queryset(...)` when the model has its own QuerySet, e.g. `EventManager`, `DojoManager`). A new model whose `__str__` follows a relation does the same; `core.tests.StrNeverQueriesTests` lists every such model.

### Geo search: MySQL spherical distance

Always use `geo.functions.DistanceSphere` for a distance-based query against a `PointField` — never Django's built-in `Distance()` (silently wrong on MySQL) and never compute distance in Python; Nominatim geocoding goes only through `geo.geocoding.geocode` (the one-request-a-second limit). Full detail in `geo/CLAUDE.md` (loaded automatically when working there).

**Caching: data, never whole pages, always cleared on save** (`CAPACITY.md`, "Caching"). Pages carry a CSP nonce, a CSRF token and the per-account nav, so a page is never cached whole: cache the data behind it. A new cache goes through `core/caching.py` (`cached(key, build, timeout, name=)`, `clear(*keys)` now and again on commit, `clear_on_change(keys, *models)` for the receivers), which also counts its hits and misses for `/metrics/`. What's cached: the dojo finder's default list (`dojos.search`) and the upcoming-sessions carousel (`events.search`) and the events list's unfiltered first page, cleared by `events/signals.py` on every save/delete of a `Dojo`, `Event` or `Registration` (`clear_default_search_cache`, `clear_upcoming_cache`, `clear_event_list_cache`); the site-wide content in `content/cache.py` (pathways, the organisation's team, global FAQs, testimonials, sponsors, and `promotions_showing(placement)`, kept only until the next promotion starts or ends); a dojo's public page in `dojos/public_cache.py` (the dojo, pathways, FAQs, updates and team; the next session's places and the join button stay live); the organisation's sign-in policy (`accounts.sign_in.policy`); and what the nav shows about the logged-in account (`accounts/navigation.py`, per account, read by `user_roles` and `accounts.manage_nav.request_manage_contexts`). **The account navigation cache never decides access**: `dojos.access`, `require_area` and `require_organisation_context` ask the database, so a stale nav can show a link for a few minutes, never open a page. Sessions are `cached_db` (read from Redis, written to MySQL too, so an emptied cache logs nobody out). `QuerySet.update()`/`bulk_create()` send no signals: call the clear function yourself after one, or live with the timeout. A test that creates a `SignInRequirement` clears the cached policy in its cleanup (`TwoStepTestMixin` does), since a rollback sends no signal. List models use `Event.objects.with_confirmed_count()` wherever `places_left` shows (otherwise one query per row); `pages.tests.DataCacheTests` holds the public pages' query counts as guards. **Redis is bounded** (`.devcontainer/docker-compose.yml`: `maxmemory 128mb`, `volatile-lru`, the container at 256 MB; production should match, `CAPACITY.md` finding 6): when full, only keys with a timeout are evicted, so the broker's queues are safe and **every cache key needs a timeout** (never `cache.set(key, value, None)`).


### Forms: Django's form templates

Button-only forms (attendance, status changes, Remove) stay plain HTML. ### Security headers: HTTPS, Content-Security-Policy, Permissions-Policy

All in `website/settings.py`, next to `COOKIE_DOMAIN`. **HTTPS:** Django trusts the proxy's `X-Forwarded-Proto` (`SECURE_PROXY_SSL_HEADER`; `TRUST_X_FORWARDED_PROTO=false` switches it off), session and CSRF cookies are `Secure` (`SECURE_COOKIES=false` only for a plain-http run on the host), and the redirect and HSTS come from the environment (`SECURE_SSL_REDIRECT`, `SECURE_HSTS_SECONDS`, `SECURE_HSTS_INCLUDE_SUBDOMAINS`; off by default, set in production's `.env` as `.env.example` explains; `scripts/deploy.sh` reports what `check --deploy` still misses). No HSTS preload (`security.W021` is silenced on purpose). **Content-Security-Policy** (Django's own `ContentSecurityPolicyMiddleware`, `CONTENT_SECURITY_POLICY`; `CSP_REPORT_ONLY=true` sends it report-only): scripts only from our static files or an inline `<script nonce="{{ csp_nonce }}">` (the `csp` context processor gives every template rendered with a request its nonce), so **never an inline handler** (`onclick=`, `onsubmit=`, ...: put `data-confirm="Question?"` on the form or its submit button, `data-autosubmit` on a select, or `data-action="reload|print|close-details"` on a button, all handled in `bundle.js`; anything else gets a listener in `bundle.js`) and **never `hx-on` or `js:` values**: htmx runs those with `eval`, which the policy forbids (`allowEval` is off in the page shells' `htmx-config` meta tag). A script inside an htmx fragment doesn't run either (its nonce is another request's): wire it from `bundle.js`. Inline styles and `style="..."` stay allowed. Images may also come from OpenStreetMap's tiles (the admin map); anything else from another site needs a policy change, which is on purpose. django-silk's pages (development only) go without the policy (`website/urls.py`). The management shell's `<body hx-headers>` sends the CSRF token with every htmx request, since the bell's form can arrive over the WebSocket without one. **Permissions-Policy** (`django-permissions-policy`, `PERMISSIONS_POLICY`): unused browser features off; geolocation (the dojo finder), passkeys and fullscreen for our own pages only. `core.tests.SecurityHeadersTests` checks all of it, including a scan of every template for inline handlers.

### htmx widgets, not a JS SPA

Per-project convention: reach for htmx for anything that needs server-driven partial updates; use native HTML/CSS for pure client-side behavior (toggles, etc.); only hand-write JS when neither covers it (hardware APIs, instant local state, scroll/viewport-only logic). `pages.views.home` is the clearest example — it renders initial state for two independent htmx-driven widgets that each re-fetch themselves against their own endpoint rather than the page reloading:
- **Dojo finder** (`dojos.views`, form in `dojos/forms.py`) — searches post to a widget view that re-renders just the results partial.
- **Upcoming sessions carousel** (`events.views.upcoming_sessions_widget`, paged via `events.search.upcoming_available_events` / `WIDGET_PAGE_SIZE`) — further pages lazy-load over htmx as it's scrolled.

**Third-party browser libraries are served from our own static files, never a CDN** (no extra connection, and visitors' IP addresses don't go to a third party): htmx and its WebSocket extension in `core/static/core/vendor/htmx/`, OpenLayers for the admin's map widget in `geo/static/geo/vendor/ol-<version>/`, and the two typefaces `tokens.css` names (Nunito, Fredoka; variable woff2 files, `core/static/core/fonts/fonts.css`, linked and preloaded before `tokens.css` in the three page shells; `core.tests.FontsTests`). Each folder's README says where the files come from (the npm package, checked against the registry's checksum) and how to upgrade; the version is in the file or folder name, so an upgrade gets a new URL. `core.tests.VendoredHtmxTests` and `geo.tests.MapWidgetAssetsTests` fail on a script from another site or a path that doesn't exist. The only outside content left is the admin map's OpenStreetMap tiles.

### Background jobs: two Celery workers, beat embedded

Celery (`website/celery.py`, loaded from `website/__init__.py` so `@shared_task` binds to it) runs background and scheduled work. Configuration is the `CELERY_*` block in `website/settings.py` (`config_from_object(..., namespace="CELERY")`):

- **Two workers, two queues** (kept lean, same in dev and production; design in `DATA_MODEL.md` §11, "Production: two Celery workers as a Level27 worker component"):
  - The `periodic` worker (`-Q periodic -B`) runs beat embedded, plus every task beat triggers. `CELERY_TASK_ROUTES` is built from `CELERY_BEAT_SCHEDULE`, so a scheduled task is routed to `periodic` automatically.
  - The mailing worker (`-Q celery`) runs everything else on the default queue. A new task needs no routing.
  - Both run with concurrency 1. Keep periodic jobs short: a slow one holds up the 10-second mail dispatcher, so a heavy job only enqueues its real work on the default queue. Never add `-B` to the second worker, or every job fires twice.
- **Broker:** Redis db `CELERY_BROKER_DB` (default 2). The cache is db 0 and Channels db 1, so a `cache.clear()` can't drop queued tasks.
- **Delivery:** `acks_late` plus `reject_on_worker_lost` (and a prefetch of 1), so a task whose worker dies halfway is handed out again. Write tasks to be safe to run twice. The exception is a heavy nightly job that would only fail the same way again: `events.tasks.rebuild_engagement` is acknowledged when it starts and has its own `time_limit` (`CAPACITY.md`, "Load: Celery workers and mail"). Heavy jobs work in batches, each in its own transaction, so their memory follows the batch: the Celery component has about 512 MB on Level27, where the kernel throttles every process in it instead of killing one.
- **Results:** `CELERY_TASK_IGNORE_RESULT = True`. Tasks report through the rows they change (e.g. `EmailMessage.status`), not through results. The `django-db` result backend stays configured for any task that opts in with `ignore_result=False`. `CELERY_TASK_TIME_LIMIT` is 30 minutes.
- **Time zone:** `CELERY_TIMEZONE = "Europe/Brussels"`, so crontab schedules are in Belgian local time. Django itself stays on `TIME_ZONE = "UTC"`.
- **Schedule:** `CELERY_BEAT_SCHEDULE` in settings is the only place jobs are defined (no `add_periodic_task` calls). Beat uses `django_celery_beat`'s `DatabaseScheduler`, which copies that dict into the `PeriodicTask` table at startup; you can edit it in the Django admin (*Periodic tasks*). It never deletes an entry the code stopped defining: remove stale ones with a data migration, as `mailing/migrations/0005_…` does. Beat only *sends* a task by name; a misspelled name shows up in the worker log as "Received unregistered task".
- **Tasks:** `autodiscover_tasks()` picks up each installed app's `tasks.py`: `mailing/tasks.py` (the mail queue, bounces, automated mail), `campaigns/tasks.py` (campaigns and journeys, under their old `mailing.tasks.…` names), `events/tasks.py` (the nightly engagement rebuild) and `privacy/tasks.py` (the daily retention job) and `applications/tasks.py` (the background-check expiry reminder and the reviewers' daily mail) and `monitoring/tasks.py` (the daily capacity sample).

**Dev processes:** `.devcontainer/start.sh` starts both workers in the background before `runserver`, logging to `/workspace/celery-periodic.log` and `/workspace/celery-mailing.log` (gitignored). Nothing supervises or autoreloads them, unlike `runserver`: **after changing a task or the schedule, restart them**, or they keep running the old code (a stale worker is exactly how you get "unregistered task" errors). From a workspace shell (run the `pkill` on its own: `pkill -f` also matches a shell whose command line contains the pattern):

```sh
pkill -f "[c]elery -A website worker"
celery -A website worker -n periodic@%h -Q periodic -c 1 -B --scheduler django_celery_beat.schedulers:DatabaseScheduler -l INFO > celery-periodic.log 2>&1 &
celery -A website worker -n mailing@%h -Q celery -c 1 -l INFO > celery-mailing.log 2>&1 &
celery -A website inspect active_queues   # which worker listens to which queue
celery -A website inspect registered      # what the running workers actually know
```

**Production:** the same two workers run as Level27's worker component *celery* (the periodic one logs at WARNING: at INFO its 10-second dispatcher fills the log; dev keeps INFO), restarted by every `scripts/deploy.sh` run (see "Deploying"); their commands live in the Level27 panel, not in the repo, so a change to them (flags, the Python path) is made there; dev starts them from `start.sh`. Level27's Redis is the broker. They share the machine's memory with gunicorn, so they recycle their child processes and run at lower priority. **Every mail the site sends goes through them**: if they're down, mail waits in the queue (nothing is lost).

**Tests:** no `CELERY_TASK_ALWAYS_EAGER` override exists. Test a task by calling the function directly (`send_pending_emails()`), not `.delay()`, which would need a broker.

### Privacy: every field is classified

Every concrete field (and many-to-many field) of every installed model, ours and third-party, has a GDPR classification in the registry (`core/privacy_registry.py`, `DATA_MODEL.md` §16): each app's `privacy.py` (autodiscovered by `privacy.apps.PrivacyConfig`; Django's and third-party models are in `privacy/privacy.py`) calls `register(Model, purpose=, legal_basis=, retention=, seen_by=, fields={...}, not_personal=[...])` or `register_not_personal(Model, reason)`. A personal field is `personal(category)` (emptied on erasure, or its row deleted for a required link to the person), `anonymise(category, replacement)` or `keep(category, reason)`, with `export=False` for what a person's data export must never include (secrets, the background-check document). Categories: `identity`, `child`, `special` (art. 9, health), `criminal` (art. 10), `profiling`, `public_profile`, `contact_public`, `security`; retention rules are named in `RETENTION_RULES`. **A new field or model needs its classification in the same change**: `privacy.tests.EveryFieldIsClassifiedTests` fails on anything unclassified, and a mistake in a declaration (unknown field, a `keep` without a reason) raises at startup. Tuple keys classify several fields alike, but there is deliberately no default for a model's fields. `manage.py privacy_register [--format csv] [-o file]` writes the register of processing activities from it. **A person's export** (`privacy.export.export_person(user)`, GDPR art. 15/20) reads only the registry too: every model with `subjects` (`{Subject.ACCOUNT: "user", Subject.CHILD: "ninja", Subject.EMAIL: "email"}`, lookups from the model to the account, a child, or the account's address) gives its rows for the account and `privacy.export.children_of(user)` (an adult's children, a ninja login's own record only), every field except the id and those marked `export=False`; links show as the linked object's `str()`. So a new model with personal data needs `subjects` too, or its reason in `privacy.tests.ExportCoverageTests.EXCEPTIONS`; a link to *someone else* (a reviewer, whoever marked attendance) is `export=False`. Families download it from the account page (`download_my_data`, `/account/data/`, once a minute per account through the cache; a ninja login from its own page), the organisation from *Accounts → Privacy* (`/manage/privacy/`, search by name, email or a child's name). **Erasure** (`privacy/erasure.py`, §16 phase 5) reads only the registry too: `erase_person(user, requested_by=None, reason=..., keep_visible=False)` finds every row by `subjects` (the account, the children only it is a guardian of, their own logins, the address), then empties `personal` fields (a required `personal` link to the person deletes the row), applies `anonymise` replacements (a literal with `{pk}`, or a `Computed`) and leaves `keep` fields; `User` and `Ninja` rows are anonymised, never deleted. `keep_visible` (champions and mentors) freezes `team_name` into `display_name` and keeps `public_profile` fields where the model's `visible_when` flag is on. It runs with the audit log disabled, clears or removes the entries about the erased rows, and writes a `privacy.ErasureRecord` per account and child (no personal data) for `manage.py privacy_replay_erasures` after a backup restore. So a new field is covered by its classification; a field whose empty value isn't obvious (not nullable, no default, not text) raises. **Deleting an account on request** is `privacy/deletion.py` (`preview()`, then `delete_account()`; `DeletionError`): the family's *Delete my account* (`/account/delete/`, confirmed with the password) and the organisation's *Delete…* on `/manage/privacy/` (`/manage/privacy/<id>/delete/`, confirmed by typing the username). Not for a champion of an active dojo, an organisation role, a superuser or a ninja's own login. **Retention** (`privacy/retention.py`, §16 phase 4): the daily `privacy.tasks.apply_retention` (10:00, default queue; `manage.py apply_retention` runs it by hand) erases an account two years after its last login (`ACCOUNT_RETENTION_DAYS`; a guardian's counts its children's own logins too, `with_inactive_since`), after reminder mails 30 and 7 days before (`account_deletion_reminder`, each recorded as a `privacy.RetentionNotice`; never sooner than 30 days after the first), cleans a champion's or mentor's instead (`keep_visible`), and leaves organisation-role holders and superusers alone. A child's own login has no date or reminder of its own: it goes with the family, and the guardian's reminder says so. The job never handles a ninja login itself: a child always has a guardian (family sign-up and Add a child create both in one transaction), and one without is a manual fix in the admin that the automatic jobs leave alone. A champion of an active dojo is held back until the role moves: the dojo's mentors get notifications, and the organisation sees them under *Needs attention* on `/manage/privacy/` (with a count on the sidebar link). The same job removes audit log entries with no account behind them after `AUDIT_LOG_RETENTION_DAYS` and expired login sessions, and clears a mail's content `MAIL_CONTENT_RETENTION_DAYS` (365) after it was created (`clear_old_mail_content`, the `mail_content` rule: the `EmailMessage` fields classified `personal`, so the account link, address, subject, body, idempotency key and Message-ID, emptied in primary-key batches with `QuerySet.update()`; the row stays for the statistics, mail still pending or sending is left alone); the other `RETENTION_RULES` wait for their periods (their texts say so: "Not decided yet"), but their removals are built (the end of `privacy/retention.py`: a child via `erase_child`, rejected applications, background-check decisions, engagement stage changes, bounce records, read notifications, the Django admin's log) and run in the same job once their setting holds a period (`CHILD_RETENTION_DAYS`/`_AGE`, `APPLICATION_RETENTION_DAYS`, `BACKGROUND_CHECK_HISTORY_RETENTION_DAYS`, `ENGAGEMENT_CHANGE_RETENTION_DAYS`, `BOUNCE_RECORD_RETENTION_DAYS`, `NOTIFICATION_RETENTION_DAYS`, `ADMIN_LOG_RETENTION_DAYS`; `None` = off); deleting a model the audit log records runs under `disable_auditlog()`. `team`, `team_attendance` and `registration` have no removal on purpose (history points at them; erasing the person anonymises them). **Every period in force is in one table**, `DATA_MODEL.md` §16 "Retention periods, as the code has them", with the setting or constant behind it, and the organisation's help-centre page `docs/source/organisation/privacy.rst` ("How long data is kept") says the same in plain words: a change to a period, or a new rule, updates both and the rule's `RETENTION_RULES` text in the same change.

### Audit log (django-auditlog)

Who changed what, and who viewed the most sensitive data, in `auditlog.LogEntry` (`DATA_MODEL.md` §14; `core/audit.py`). **Recorded models are `core.audit.RECORDED`** (with `exclude_fields`/`mask_fields`/`m2m_fields`), registered from `CoreConfig.ready()` with an explicit `include_fields` (auditlog 3.4.1 otherwise diffs reverse relations); every other model is in `core.tests.AuditLogCoverageTests.NOT_RECORDED` with its reason, so **a new model needs a decision there**. The actor comes from `core.audit.AuditlogMiddleware` (auditlog's, minus the port; `AUDITLOG_DISABLE_REMOTE_ADDR` keeps IP addresses out). Health notes and secrets are masked entirely (`core.audit.mask`). Rules:
- Only `save()`/`delete()`/many-to-many changes are recorded, never `QuerySet.update()` or `bulk_create()`: a change to a recorded model that should show up in the log goes through `save()` (as *Mark all present* does).
- A new view that shows special-category data (health, criminal records) or hands out someone's data records it: `core.audit.log_access(obj)` in the view, `{% load audit %}{% audit_view obj %}` inside the template block that prints it (the attendance list's health notes), or `LogAccessAdminMixin` on a ModelAdmin. Nothing else is logged as a view.
- Seed commands wrap `handle` in `@without_audit_log`; Celery jobs and other commands record with an empty actor.
- **Read-only, for the organisation's admin role** (`auditlog.logentry` view in `accounts.organisation.ADMIN_PERMISSIONS`, never the board) and superusers, in two places: the organisation dashboard's *Audit log* (`/manage/audit-log/`, `pages/audit_views.py`, the `audit_log` area, whose permission is that same view permission; filters by person or item, kind of change and kind of data, 50 per page), which shows every value through `core.audit.display_changes` and hides as `****` whatever `core.audit.is_hidden` says: fields the privacy registry classifies `special`, `criminal` or `security`, the `mask_fields`, and anything the registry has no decision about (so a new sensitive field is hidden once it's classified; `export=False` alone doesn't hide, since it also marks who did something); and the Django admin's log (auditlog's stored values, masked fields as `***`); `AuditHistoryAdminMixin` adds a per-row "Audit log" column (User, Ninja, Dojo, Event admins) with the same check. Families aren't told about it and it isn't in their export.
- Retention and erasure (`privacy.retention`, `privacy.erasure`): an account's entries (made by it, or about its rows) are removed when the retention job erases it two years after its last login, and cleared when it's erased on request; entries with no account behind them go after `AUDIT_LOG_RETENTION_DAYS`. An erasure itself is never recorded (its diff would hold what was erased). `manage.py auditlogflush` is the emergency tool.

### Sensitive vs. public media

`MEDIA_ROOT`/`MEDIA_URL` (photos, icons, event images) are public and served directly under `DEBUG` (`website/urls.py`); in the devcontainer nginx serves them from disk either way (`.devcontainer/nginx/nginx.conf`, which mounts `media/`, never `private_media/`). `PRIVATE_MEDIA_ROOT` (background-check documents only) has no corresponding `url()` pattern anywhere — don't add one. If a new feature needs to store a sensitive file, use `applications.storage.private_storage` (or the same `base_url=None` pattern) and gate reads through a permission-checked view, not a media URL.

**Uploads go through `core/uploads.py`** (`CAPACITY.md`, "Disk: files and uploads"). An image people upload is a `core.uploads.UploadedImageField` (never a plain `ImageField`), with a `max_side` (`BANNER_SIDE` 1600, `LOGO_SIDE` 800, `ICON_SIDE` 512): `validate_image_upload` refuses more than 10 MB or 40 megapixels (also in the Django admin; a row's existing file isn't checked again), and on save the image is made smaller and rebuilt from its pixels alone (JPEG, or PNG with transparency), so no metadata survives: EXIF with a photo's GPS position, XMP, comments, text chunks, colour profiles (the orientation and colour profile are applied first). A replaced image, or one whose row is deleted, is deleted from storage on commit, unless it's a standard image or another row uses it (`connect_cleanup`, receivers only on the models with such a field, so bulk deletes elsewhere stay fast; `QuerySet.update()` bypasses it). A form shows the limits with `with_upload_help(...)`. A document upload gets `validate_document_upload` (PDF, JPEG or PNG by its first bytes, 10 MB). The proxy caps request bodies at 12 MB (`client_max_body_size` in `.devcontainer/nginx/nginx.conf`; production's proxy is Level27's), a little above the site's 10 MB so the site's own message shows in between. Tests: `core.tests.UploadGuardrailTests`.

### Standard images: link, don't copy

The app ships standard images for event banners, dojo icons, award icons, mentor and ninja avatars and pathway images. Each set lives under its app's `static/` folder with a module listing its `(filename, label)` pairs: `events.template_images` (banners), `dojos.template_icons` (dojo icons), `accounts.template_avatars` (`TEMPLATE_AVATARS` for adults, `TEMPLATE_KID_AVATARS` for ninjas). Badge icons (`events/seed_data/awards/`) and pathway images (`pathways/seed_data/images/`) stay seed data: they're designed and enabled by the team, not picked by users. `core/image_library.py` maps each kind to its folder (`LIBRARY_DIRS`), which each app fills from its `AppConfig.ready()` with `register_library` (core knows no app). **Using one never copies it:** `use_library_image(instance, field, kind, filename)` points the `ImageField` at `library/<kind>/<filename>` in media storage, which is copied there once, the first time any row uses it (no deploy step). Every row that picks the same template shares that one file. Only a file someone uploads themselves goes through the field's `upload_to` and gets its own copy. The form pickers (`DojoProfileForm.template_icon`, `EventForm.template_image`, the ninja avatar dropdown in `accounts.forms.ChildForm`, which on an edit offers "Keep the current photo" when the photo isn't a standard one, so saving never replaces an upload) and every seeder use it, and `library_filename(fieldfile, kind)` preselects the current template in a picker. Library files are shared: never `.delete()` one through a model field (`is_library_image()` tells the two apart). Tests that save files mix in `core.testing.TempMediaMixin` (a throwaway `MEDIA_ROOT`; the test's own `setUp` must call `super().setUp()`).

### i18n

`LANGUAGES` is `en-us`/`nl-be`/`fr-be` (German was dropped until German texts can be checked; also the mail languages, `User.preferred_language`). `LocaleMiddleware` picks the site's language (the language cookie, then the browser's `Accept-Language`); the switcher in `core/templates/core/menu.html` posts to Django's `set_language`, which only sets that cookie. **The site language and the mail language are separate (decided):** logged in or not, the site follows the cookie; an account's `User.preferred_language` is only its mail language, and the switcher never changes it. **The site's texts live in one project catalog per language, `locale/{nl_BE,fr_BE}/LC_MESSAGES/django.po`** (`LOCALE_PATHS`); the compiled `django.mo` is committed (the server may have no gettext), so after editing a `.po` run `compilemessages` and commit both.

- **A dojo's own texts are in the dojo's languages** (`DATA_MODEL.md` §19): `Dojo.languages` (ordered, first = main language; also the languages its sessions are given in, shown and filterable), and `Dojo`/`Event`/`Announcement` are `core.content_languages.TranslatableModel`s: main language in the normal columns, others in `translations`. Show them with `{% load content_i18n %}` `{{ obj|localized:"field"|in_lang }}` (`in_lang` marks a fallback text with its `lang`, WCAG 3.1.2; never inside an attribute or `<title>`) (+ `{% only_in text %}` for the fallback note), never the raw field on a public page; forms add the per-language fields with `add_translation_fields`/`save_translation_fields` and include `dojos/partials/_translation_fields.html`. A new translatable text is a `TRANSLATABLE_FIELDS` entry, not a new column. The organisation's own content does the same in `settings.ORGANISATION_LANGUAGES` (`OrganisationContent`: pathways, steps, projects, skills, belts, badges, team listing, promotions; `ScopedContent`: FAQs and testimonials follow their dojo when scoped to one), edited through `core.admin_translations.TranslationAdminMixin` in the admin (put it first in a ModelAdmin's bases for any new translatable model).
- **Everything a person sees is translated:** every template (public, family, volunteer applications, the dojo team dashboard, the organisation dashboard), the Python texts they show (forms, messages, model choices, `TeamError`/`OnboardingError`/`CampaignError`/`BeltError`/`ChildAccountError`, the segment builder's attribute labels, operators and rule sentences), dashboard notifications and `bundle.js`. **Not translated through the catalogs:** anything stored in the database; the dojo's own texts follow its languages (above), so does the organisation's content (pathways, FAQs, badges, belts, testimonials, team listing, promotions); segment and template descriptions are shown as written; model `help_text`/`verbose_name` (the Django admin, which Django itself translates); mail templates (their own rows per language).
- **Notifications are stored text**, so `notifications.services.notify(recipient, gettext_lazy("... %(dojo)s ..."), params={...})` renders them in the *recipient's* `preferred_language`, not the acting user's; `dojos.team.notify_managers` passes `params` through. Never pass an f-string or an already-translated `_()` string.
- **`bundle.js`** uses Django's JavaScript catalog, loaded before it in the three page shells from `/jsi18n/<language>/<version>/` (`core/jsi18n.py`, `{% load js_catalog %}{% javascript_catalog_url %}`): the language is in the URL rather than the cookie and the version is a hash of the compiled `djangojs.mo` files and the Django version, so browsers cache it for a year (`immutable`) and new translations get a new URL (also on a running runserver, which doesn't restart for a `.mo` file). The plain `jsi18n/` (`JavaScriptCatalog`) still works, and it calls `gettext("...")` (falling back to the English text without the catalog). Its strings live in `locale/*/LC_MESSAGES/djangojs.po` (`makemessages -d djangojs`).
- **Tone:** Dutch uses informal "je" everywhere (also to parents); French uses "vous". Keep a text's HTML/placeholders identical in translations.
- **Marking texts:** `{% load i18n %}` in every template that has any (includes don't inherit it); `{% translate "..." %}` for plain text, `{% blocktranslate with x=... %}` for text with variables (no filters inside the block: bind them in `with`), `count counter=...` + `{% plural %}` for plurals. In Python, `gettext_lazy as _` for module-level strings (choices, form labels) and `gettext as _` in views, with named placeholders (`_("%(name)s ...") % {...}`), never f-strings. A text built per form or per row that must stay lazy (a label with a name in it) calls `django.utils.functional.lazy()` **once, at module level**, and the function it returns per object (`dojos.forms.note_placeholder_lazy`): every `lazy()` call defines a new class of about 30 KB that only a full garbage collection frees (`MEMORY_PROFILE.md`); `core.tests.LazyOnlyAtModuleLevelTests` fails on a `lazy()` call inside a function. A lazy label that's joined or `.lower()`ed needs `str()` first. JS strings in a template: `{% translate "..." as var %}` then `"{{ var|escapejs }}"`, with `{name}` placeholders replaced in JS (a `%s` in a template `translate` string gets mangled). Never write a template tag inside a JS comment in a template: it's parsed.
- **Workflow:** `python manage.py makemessages -l nl_BE -l fr_BE --ignore=".venv/*" --ignore="docs/*" --ignore="staticfiles/*" --ignore="media/*"` (and the same with `-d djangojs` after changing `bundle.js`), translate the new entries and replace the *fuzzy* guesses gettext pre-fills (they're usually wrong, and `compilemessages` skips them), keep the header free of `#, fuzzy` (or the French plural rule is dropped), then `python manage.py compilemessages -l nl_BE -l fr_BE --ignore=".venv/*"`. Django's own texts (form errors, password rules) come translated from Django's catalogs. Mail templates are translated separately (`EmailTemplate` rows per language, `mailing/seed_templates.py`); the help docs too (`docs/`).
