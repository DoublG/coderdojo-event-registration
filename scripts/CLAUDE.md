### Deploying (Level27)

Production is Level27 Python hosting, reached over SSH with key auth (`py10102@c40a7b15f.l27powered.eu`). `scripts/deploy.sh --check` is a read-only preflight; `scripts/deploy.sh` does the real deploy. It bundles the working tree (dev-only paths excluded), installs `requirements.txt` into the **pyenv env gunicorn runs from** (`~/.pyenv/versions/py10102-3.14.7`, *not* `~/app/.venv`), runs `manage.py check` on the new code *before* touching the live app, rsyncs into `~/app` (keeping `.env`, `media/`, `private_media/`, `staticfiles/`), migrates, runs `collectstatic` (production's `.env` sets `STATIC_ROOT=~/app/staticfiles`, which Apache serves at `/static/`, and `media/` at `/media/`, through the app's *Extra Apache configuratie* in the Level27 panel), then puts the new code live and smoke-tests over the unix socket. The app is the systemd service `py10102.service` with the server chosen in the Level27 panel (`main:app` on `/var/run/socket/py10102.socket`, from `~/app`), reachable only through a URL linked to the app in the panel (*Gekoppelde URL's*; without one Apache shows Level27's placeholder page): **daphne** since 6 October 2026, which can't reload, so the deploy stops it and systemd starts it again (`Restart=always`, 30 s: half a minute down), or gunicorn (`gunicorn -k uvicorn.workers.UvicornWorker main:app`), which gets a graceful HUP; `deploy.sh` handles either. The repo-root `main.py` just re-exports `website.asgi.application` as `app`. Under gunicorn, gunicorn reads the repo-root **`gunicorn.conf.py`** from `~/app` by itself: it caps each uvicorn worker at `UVICORN_LIMIT_CONCURRENCY` (25) connections, beyond which uvicorn answers 503 at once, so the site's MySQL connections stay under the limit (every request in progress holds one; `CAPACITY.md`, "Capping requests per web worker"; the devcontainer's DEBUG-off gunicorn reads it too). `deploy.sh --check` and every deploy say whether gunicorn really reads it (not when it starts elsewhere or with a `-c` of its own). The bundle leaves out `user-journeys/` and `loadtest/` (tooling, not the site). uvicorn only accepts WebSockets (the notification bell) with `websockets` installed, hence that package in `requirements.txt`; without it every `/ws/` connection gets a 404. Production env vars live in `~/app/.env` on the server. To replace it, put a local `.env.production` (gitignored via `.env.*`) next to the script and it gets uploaded. **Celery workers:** Level27 runs them, not the deploy: we can't create systemd units of our own there, so both commands are in the project's worker component *celery* (*Optioneel component* in the panel, one *Commando* per worker, each starting with `cd /var/python/py10102/app && `, since its scripts in `~/.worker/` start in the home directory; output in `~/logs/worker-<id>/`), which starts a worker again whenever it stops. Every deploy restarts them with a warm shutdown (SIGTERM to each main process: the task in hand finishes, Level27 starts it on the new code) and pings them; `--check` lists them. All mail goes through them, so a deploy whose workers don't come back fails loudly after the site is live. (Earlier deploys installed systemd user units, `coolregistration-celery-*`; a deploy removes them when it finds them, since next to the component they'd be a second beat.) The server has **no MySQL client headers and no GDAL/GEOS**, so `mysqlclient` and `django.contrib.gis` can't work there until that's solved; the script's `manage.py check` step stops a deploy before it can break the live site.

**Health check for uptime monitoring:** `/health/` (`pages/health.py`, open to anyone, never cached) answers 200 `{"status": "ok", "checks": {...}}` when the database, Redis (pinged directly: the cache's `IGNORE_EXCEPTIONS` would hide it) and the mail workers (no due mail waiting past `mailing.queue_status.STALLED_AFTER`) are fine, and 503 naming the failed check otherwise (the error goes to the log, never the response). Point an external uptime monitor at it; a new check is a function in its `CHECKS`.

**Capacity and monitoring** (`CAPACITY.md`: the measured database growth, memory per component, load results, findings and how to measure again; `MONITORING.md`: every metric and Grafana panel explained, with screenshots under load in `loadtest/grafana/`, so a new metric or panel gets its row there; app `monitoring`): `/metrics/` (Prometheus text format, `monitoring/views.py`) answers only with `METRICS_TOKEN` as a bearer token and is a 404 while it's empty; it shows table sizes, MySQL's and Redis's counters, the Celery and mail queues, open WebSockets, each process's memory and per-view request and per-task timings, never anyone's data. The timings and process memory are counters in the cache's Redis (`monitoring/recorder.py`), written by `monitoring.middleware.RequestMetricsMiddleware` (first in `MIDDLEWARE`; also logs requests over `METRICS_SLOW_REQUEST_MS`) and Celery's signals (`monitoring/celery_signals.py`); recording never fails a request or task (`METRICS_ENABLED=false` switches it off). The beat job `capacity-sample` (02:30, `periodic`) stores the day's figures as a `monitoring.CapacitySample`. `manage.py capacity_report` (read-only, fine on production) prints the database now and its projection per scenario (`monitoring/capacity.py`: `SCENARIOS`, and in `GROWTH` the rows each growing table gains per year); **a new table that grows with use gets its `GROWTH` entry**. The bytes per row in `monitoring/row_sizes.json` come from `manage.py seed_scale` (a scenario's data, only in a database whose name starts with `test_`) and `capacity_report --measure`. The load test is `loadtest/` (Locust and matplotlib in a venv of their own, `loadtest/requirements.txt`; never in the image or on production): `run.sh` runs one Locust run and samples `/metrics/` (`sample_metrics.py`), `summarize.py` condenses a folder of runs into `loadtest/results/<date>.json`, `charts.py` draws `loadtest/charts/` (in `CAPACITY.md` and the technical PDF), run against a production-like gunicorn on that database with `REDIS_CACHE_DB`/`REDIS_CHANNELS_DB`/`CELERY_BROKER_DB` of its own (the steps in `CAPACITY.md`, "Measuring again"). Its `mixed` and `rush` modes log in and book, so `locustfile.py` refuses them against any host that isn't local; **only its `public` mode (visitors, nothing written) may run against production** (`CAPACITY.md`, "Load testing production").

**CI (GitHub Actions) runs the checks, never a deploy** (deploys stay local, `scripts/deploy.sh`). Four workflows: `.github/workflows/tests.yml` (**Tests**: `makemigrations --check` and the whole suite with `--debug-mode`, on every push and pull request that changes code, against `mysql:8.4` and `redis:7.2` services with the devcontainer's settings as env vars; it runs with `--testrunner xmlrunner.extra.djangotestrunner.XMLTestRunner` (unittest-xml-reporting, dev only), which writes `test-results/junit.xml` (`TEST_OUTPUT_DIR`), and `.github/scripts/test_report.py` turns that into the run's summary (per app, failed tests with their traceback, the slowest) and an `::error` annotation on each failing line, even when the tests failed; the XML is kept 30 days as the `test-results` artifact and the README's badge shows main's result. Locally the same: add the `--testrunner` and run the script, which prints the summary when `GITHUB_STEP_SUMMARY` isn't set), `.github/workflows/audit.yml` (**Code audit**: on pushes to main, pull requests, every Monday and by hand; `ruff check` + `ruff format --check`, ruff's security rules `ruff check --extend-select S .`, `mypy` (the `types` job, with the site's requirements, since the plugin starts Django), `pip-audit` over both requirement files, `manage.py check --deploy` with DEBUG off (warnings go to the run's summary, only errors fail) and CodeQL into the repository's Code scanning; details in `MAINTENANCE.md`, "Code audits"), `.github/workflows/quality.yml` (**Code quality**: every Monday and by hand, the suite under coverage plus radon's complexity and maintainability, condensed by `quality/summarize.py`; `.github/scripts/quality_report.py` writes the run's summary with the change since the previous run, whose artifact it fetches; the JSON and coverage's HTML are kept 90 days as the `quality` artifact; a map, never a gate: only failing tests fail it) and the help centre's (below). Keep them passing: a new security-rule finding on a line that's fine gets `# noqa: Sxxx` with its reason (tests, seeders, `user-journeys/` and `loadtest/` are left out in `pyproject.toml`), and an advisory that isn't reachable here gets an `--ignore-vuln` in `audit.yml` only together with its row in `MAINTENANCE.md`'s security log. A new setting read with `env(...)` and no default needs a value in both workflows' `env:` too.
