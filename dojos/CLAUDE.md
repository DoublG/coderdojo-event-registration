### Dojo admin area (champions and mentors)

A dojo's admin screens (`/dojos/<id>/dashboard/` = attendance, `/dojos/<id>/manage/` = profile settings, `/dojos/<id>/events/` = events list, `/dojos/<id>/events/new/` = create an event, `/dojos/<id>/events/<event_id>/` = edit an event, `/dojos/<id>/events/<event_id>/attendance/` = take attendance for that event, `/dojos/<id>/manage/team/` = the Team page, `/dojos/<id>/manage/updates/` = the Updates page (post/remove the "From this dojo" notes, `content.Announcement`, dated the day they're posted; the public page shows the newest `PUBLIC_UPDATES_LIMIT` = 5), `/dojos/<id>/manage/lifecycle/` = the champion's status actions, `/dojos/<id>/manage/members/` = the Members page (children whose home dojo it is, with a Promote-to-youth-mentor button), `/dojos/<id>/manage/api/` = the API page (the dojo's API clients, champion only; views in `api/views.py`), `/dojos/<id>/manage/mail/` = the Mail page (the dojo's own mail to its families, `DATA_MODEL.md` §25: every role reads it, writing and sending need `SEND_MAIL`, the champion; views in `campaigns/dojo_views.py`, form `campaigns.forms.DojoMailingForm`, audiences `campaigns/dojo_audiences.py`)) all extend `dojos/templates/dojos/_admin_base.html`, which extends the management area's shared shell `core/_manage_shell.html` (see "One management area" below; it doesn't extend `core/base.html` — this is an app-like admin surface with its own collapsible-sidebar layout via `CoderDojo.initAdminNav`, not a scrollable marketing page). The page scrolls naturally (no inner fixed-height/`overflow` scroll container) — `.cd-admin-nav`'s height comes from the shell's default flex `align-items: stretch` matching `.admin-main`'s natural content height, so the sidebar's background/border always run the full length of the page, however long that page is. Sidebar markup matches the CoderDojo design system's `AdminNav`/`AdminDashboard` components. A page extending it fills `admin_page_title`/`admin_heading`/`admin_content` (and optionally `admin_topbar_extra`, `admin_extra_style`/`admin_extra_script`) and passes an `active` context var (`"attendance"`, `"settings"`, `"events"`, `"team"`, `"updates"`, ...) matching the sidebar link it should highlight. Every view here is `@login_required` and resolves its dojo through `dojos.access.require_dojo_access(request, dojo_id, capability)` — **never `get_object_or_404(Dojo, ...)` alone** for an admin view, or anyone can reach it by guessing an id — and renders with `dojos.views._admin_context(request, access)`.

**Who gets in, and what they can do** (`dojos/access.py`): an **active `champion` or `mentor` membership** at the dojo, held by an account whose background check is valid (`managing_membership`); youth mentors, requested and dormant memberships get nothing. No role → 404 (same reasoning as `accounts.views._get_own_ninja`); a role lacking the view's capability → 403. Capabilities: `TAKE_ATTENDANCE`, `MANAGE_EVENTS` (create/edit/status), `EDIT_SETTINGS` (`dojo_manage`), `MANAGE_TEAM` (Team page actions), `AWARD_BELTS` (phase 5), `AWARD_BADGES` (one-off badges, from the attendance list), `POST_UPDATES` (the Updates page), `MANAGE_LIFECYCLE` (launch/dormant/archive/reopen) and `VIEW_HEALTH_NOTES` (a child's allergies or notes on the attendance list); the dashboard, events list, Team page view and notification endpoints need only *a* role, leaving needs any role, and handing over the champion role is champion-only (`access.is_champion`, never a capability). `ROLE_CAPABILITIES`: champion gets everything, **mentors everything except `MANAGE_LIFECYCLE`, `VIEW_HEALTH_NOTES`, `MANAGE_API` and `SEND_MAIL`** (the dojo's API clients and its mail to the families act for the whole dojo); restricting mentors is just removing entries there. Who may *join* a team is `access.is_approved_mentor` (an approved mentor or champion `Application` plus a valid background check — `applications.services.is_approved_mentor`). Templates read `dojo_access.can_*` to hide what the viewer can't use and `dojo_access.role_label` (Champion/Mentor) for the sidebar; the sidebar's switcher lists the dojos from `accessible_dojos(user)` (including draft/dormant/archived dojos their team still manages) through `accounts.manage_nav`, which also drives `/manage/`, the post-login redirect and the nav's "Manage" link (see "One management area" below). A new admin view must pick its capability explicitly; if it's a genuinely new kind of action, add a capability rather than reusing a loosely related one.

`dojos.views.dojo_manage` (`DojoProfileForm`), the events screens below, attendance, the Team page, the lifecycle card, the Updates page, the Members page and the notification bell (below) are all wired to real data. The dashboard shows a banner for a non-active dojo, or the six-month dormancy nudge (`dojos.team.needs_dormancy_nudge`, computed per request). `dojo_manage` covers everything shown on `dojo_detail.html` (including the pathways the dojo provides, `Dojo.pathways`) except the team, `status` and `location`/`province`, which aren't self-service: an address edit is re-geocoded on save (`geo.geocoding.geocode`, same tolerant-failure pattern as `dojos.search.resolve_search_origin` — a failed/no-match geocode never blocks the save) and a successful one also refreshes `province` via `geo.geocoding.find_province` (point-in-polygon against `geo.AdministrativeBoundary`, with a nearest-boundary fallback), so a champion never touches either field directly.

**Events**: `dojos.views.dojo_event_list`/`dojo_event_create`/`dojo_event_set_status` (views live in `dojos`, not `events`, matching the rest of this admin area — same as `dojo_dashboard` reaching directly into `events.Registration`) manage `events.Event` rows for one dojo. `Event.status` (`events/models.py`) is a three-state lifecycle — `draft` (model default; hidden from the public site via `EventQuerySet.visible()`, used by every public-facing query: `event_list`, `upcoming_available_events`, `dojo_detail`'s `next_event`, `dojos.search.attach_next_events`) → `open` (registrations open, `Event.registration_open`) → `closed` (registrations closed, gated in `events.views.event_signup`). It is *not* a one-way lifecycle: `dojo_event_set_status` (POST-only) takes an absolute target `status` and sets it from any other status — the team can reopen a closed session or pull one back to draft, and existing registrations are always kept. The events list shows a one-click next step per row (Publish / Close registrations / Reopen); the event detail page (`dojo_event_detail`, edit-in-place like `dojo_manage`) shows every option in its status card, and posts `next` back to itself (validated with `url_has_allowed_host_and_scheme`). Saving the edit form never touches status. `events.forms.EventForm` (used by `dojo_event_create` and `dojo_event_detail`) has four quirks worth knowing before touching it: (1) it takes a single `event_date` field plus separate `start_time`/`end_time` *time* fields (not two datetimes) — a session can't span midnight, and this makes that structurally true rather than validated; all three render in Belgian dd/mm/yyyy + 24h HH:MM notation regardless of the visitor's own browser locale (`EventForm.save()` combines them back into the model's real `start_time`/`end_time` datetimes). (2) Its banner `image` can come from an upload or from `template_image`, a picker over `events.template_images.TEMPLATE_IMAGES` (linked from the shared image library, not copied, see "Standard images" below; the edit form preselects the one in use) (also the source seed data uses, see `seed_events.py`) — an uploaded file always wins if both are submitted. (3) `Event.team` is a `ManyToManyField` to `dojos.DojoMembership` (who runs the session — champion, mentors and youth mentors), rendered as a checkbox list scoped to the dojo's active memberships, labelled "Name (Role)", in `EventForm.__init__`. (4) `Event.pathways` is pre-selected from `Dojo.pathways` on a *new* event only (an existing event keeps its own); any pathway may be picked, the dojo's are just the default.

**Attendance**: `Registration.attended` is tri-state (`None` = not yet marked). `dojos/partials/_attendance.html` (built by `dojos.views._attendance_context`: confirmed, non-waitlisted registrations only, alphabetical) is shared by the dashboard (next upcoming session, else most recent) and `dojo_event_attendance` (a specific event, linked from its detail page's "Take attendance"). It's server-driven htmx, **not** `CoderDojo.initAttendance` (that bundle.js helper only toggles client-side and saves nothing — don't wire it up on these pages): each row's toggle posts to `dojo_event_attendance_mark` (`attended=present|absent|none`; re-clicking the pressed button sends `none`), which returns that row plus the "N of M present" summary as an `hx-swap-oob` fragment; "Mark all present" (`dojo_event_attendance_mark_all`) re-renders the whole block. Both fall back to a redirect for non-htmx posts, and resolve the registration scoped to the URL's event (and that event to the owned dojo). Each row also carries the per-ninja pathway picker (`dojo_event_registration_pathways`) and, with `AWARD_BELTS`, an "Award belt" form (`dojo_event_award_belt`), and with `AWARD_BADGES` an "Award badge" form (`dojo_event_award_badge`: the one-off badges the ninja hasn't earned yet; milestones are never offered); marking attendance (single or all) calls `events.awards.sync_milestones` so milestone badges follow it. The session's team (`Event.team`) is on the same list, under the children (`_attendance_team_row.html`, `dojo_event_team_attendance_mark`, stored in `events.TeamAttendance`, tri-state like `Registration.attended`; "Mark all present" includes them): who was actually there is the record the insurance needs. A child whose home dojo is another dojo is labelled "Visiting". With `VIEW_HEALTH_NOTES` (the champion only) a row also shows the family's `Ninja.allergies_notes` (health data, GDPR art. 9): only there, so only for children with a confirmed place at that session. The family edits it on the sign-up, add-a-child and edit-a-child forms, which say who sees it; if you widen who sees it, change that text (and the docs) too. Belts and badges are only ever awarded through `events/awards.py` (`award_belt` raises `BeltError`, `award_badge` raises `BadgeError`, both with a user-facing message; a one-off `NinjaBadge` records `awarded_by`/`awarded_as_membership`/`note` like a belt, a milestone leaves them empty) — `NinjaBelt` is an append-only history, never edited.
