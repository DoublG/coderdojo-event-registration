### Email

**Every mail goes through the mail engine** (`mailing.services.send`, queued and sent by the Celery workers; see "Mailing and segmentation"). Nothing calls `send_mail` directly: the onboarding mails in `applications.services` and the password reset (`accounts.forms.StyledPasswordResetForm.send_mail`) are `service` templates like any other, sent through `send_or_log` so a missing template is logged instead of failing the reviewer's action or the reset. `EMAIL_BACKEND` is env-driven in `website/settings.py`: console backend by default (host dev), SMTP once `EMAIL_HOST` is set. The devcontainer points it at **Mailpit** (`mailpit` service in `.devcontainer/docker-compose.yml`, SMTP on `mailpit:1025`, no auth/TLS), which catches every outgoing mail: during development and testing all mail goes there, and its UI is where you check it. Mailpit also serves as the dev bounce mailbox over POP3 (`mailpit:1110`, `MP_POP3_AUTH`) and has chaos mode on (`MP_ENABLE_CHAOS`) to simulate SMTP failures; both need the `mailpit` container recreated after changing its environment (from the host: `docker compose -f .devcontainer/docker-compose.yml up -d mailpit`). Read them at `https://coolregistration.localhost/mails/` (nginx proxies `/mails/` to Mailpit's UI; `MP_WEBROOT=/mails` has to match that prefix; Mailpit has no host port of its own). Mail is kept on the `mailpit-data` volume (max 5000 messages).


### Mailing, segmentation and the organisation dashboard

`mailing` is the site's mail engine: every mail goes through it, and campaigns are run from the organisation dashboard. `DATA_MODEL.md` §11 has the diagrams and **the plan it was built from** (every phase is done; the decisions and open points are there too): mail categories with opt-in/out, the `send()` gateway, the engagement snapshot, the segmentation attributes, `Event.audience` (a label for girls' sessions, never a signup restriction), and the phases. Follow that plan and update it as phases land.

- **Account data it uses:** `User.preferred_language` (the mail language; set at family sign-up, defaulting to the page's language; empty = English) and `User.postal_code` (optional, a Belgian postcode checked against `geo.Municipality` by `accounts.forms.clean_belgian_postal_code`; set at family sign-up and in the account page's details, not on Mail preferences; also the dojo finder's default origin, see "Geo search"). `Ninja.gender` (`girl`/`boy`/`other`/`unspecified`, default `unspecified` = "Prefer not to say") is optional on every family form (sign-up child rows, add a child, edit a child, all built on `accounts.forms.ChildForm`, whose `LenientChoiceField` turns anything unknown into `unspecified`; an edit without the field keeps the stored value). `Event.audience` (`everyone`/`girls`) is a "Girls' session" label on the public pages (`events/partials/_audience_badge.html`) and a targeting signal, **never** a signup restriction.
- **Categories** (`mailing/categories.py`, `MailCategory`): `service`, `registration`, `reminder`, `dojo_news`, `volunteer`, `newsletter`. A code enum, not a table. Per category: `CAN_OPT_OUT` (service/registration can't be switched off), `DEFAULT_SUBSCRIBED` (newsletter off until opted in, the rest on), `PRIORITY` (lower is sent first) and `ALLOWED_FOR_NINJA_ACCOUNTS` (a ninja's own login gets service/registration/reminder/dojo_news, never volunteer or newsletter mail).
- **Segments** (`Segment` → `SegmentGroup`s, nested through `parent`, each ANDing or ORing its rules and child groups → `SegmentRule`s `attribute`/`operator`/`value` JSON) describe an audience without code. A group's `scope` is `user` (rules filter accounts) or `ninja` (every rule describes *the same child*, and the group selects that child's guardians, **only those who consented for that child**, `Guardianship.consent_given_at`, see `accounts.consent`); a ninja group can only contain ninja groups. `campaigns.segmentation.resolver.SegmentResolver.resolve(segment)` returns the accounts, always limited to **active adult accounts with an email**, never ninja accounts; the root groups are ANDed, and a segment without rules resolves to nobody. **Every rule becomes its own `pk__in` subquery**, never a join in one `filter()`, so two rules over the same to-many relation stay independent. Keep it that way when touching the resolver.
- **Attributes** are `SegmentAttribute` subclasses (`campaigns/segmentation/base.py`: `key`, `label`, `value_type`, `scope`, `choices()`, `build_q(operator, value) -> Q` on the scope's model, and `validate()`; the operators per `value_type` are in `OPERATORS`). They're registered by key in `campaigns/segmentation/registry.py`. Today, on accounts: `account_role` (parent / active mentor / active champion / organisation role; one account can be several), `joined_within_days`, `account_type`, `has_children`, `active_team_member` (active champion/mentor membership at an active dojo that held a non-draft session in the last N days), `language`, `province` (including a `brussels` choice, since Brussels-Capital isn't a province in `geo.AdministrativeBoundary`), `near_dojo` (`{"dojo": id, "km": n}` from the postcode's municipality centres, via `DistanceSphere`), `ninja_gender`, `ninja_age`, `ninja_home_dojo`, `current_belt` (with a "No belt yet" choice), `has_badge`, `pathway`, `waitlisted_for_event`, `cancellations` (last 90 days, from `events.RegistrationCancellation`), `attended_within_days` (came to a session in the last N days: marked present, or a confirmed place where the dojo marked nobody), `event`, `attended_event`, and on the engagement snapshot: `engagement_stage`, `engagement_stage_at_dojo` (`{"dojo": id, "stages": [...]}`), `attendance_rate` (%), `sessions_attended`, `missed_in_a_row`, `days_since_last_visit`, `no_shows`, `has_upcoming_registration`, `main_dojo_status`. Value types: `choice`, `boolean`, `days`, `number` (`gte`/`lte`), `distance`, `dojo_stage`; each attribute also has `describe()` (the rule as a sentence) and `value_from_form()` (the builder's fields → the JSON value). `SegmentRule.clean()` validates a rule against its attribute and its group's scope. A new criterion is a new attribute class plus a registry entry; the resolver doesn't change.
- **Templates** (`EmailTemplate`): one row per `key` and `language`, with a `category`, a subject and a plain-text body in Django template syntax. `mailing.rendering.render(key, language, context)` returns `(subject, body)`, falls back to English when a language is missing, doesn't HTML-escape, and formats `|date` under the template's language (so day and month names are translated). The standard templates and a working sample context for each key are in `mailing/seed_templates.py` (`TEMPLATES`, `SAMPLE_CONTEXT`; `SYSTEM_TEMPLATE_KEYS` = the ones the site sends itself): booking confirmed/waitlisted, waiting-list promotion, session reminder, new sessions at a dojo, the five onboarding mails, the password reset, a child's new login, the login-link mails (`login_link`, `login_link_not_available`, `login_method_confirm`, `login_method_changed`, and `child_login_changed` to the guardians), a child made youth mentor (to the family), the account-deletion reminder (`privacy.retention`), and the three campaign examples, each in en/nl/fr.
- **Campaigns** (`Campaign`, rules in `campaigns/services.py`; `CampaignError` carries a user-facing message) are one mailing to a segment: a `category` (only one people can opt out of), a `template_key`, a `context` of extra template variables and an optional `scheduled_at`. `draft → queued → sending → completed` (or `cancelled`). `launch()` checks the campaign (`launch_problems`), freezes the segment's definition in `segment_snapshot` (`serialize_segment`) and marks it `queued`; the audience is always resolved from that snapshot, so editing the segment later changes nothing for a launched campaign. `launch_due` (beat, every minute, `periodic`) hands due campaigns (no `scheduled_at`, or its time has come) to the `launch_campaign` task (default queue), resumes one whose queuing was interrupted and completes those whose mail is all out. `queue_chunk` queues one mail per account that wants the category, through `send()` with idempotency key `campaign:<id>:<user>` and a cache lock, so re-running is safe, `MAILING_CAMPAIGN_CHUNK_SIZE` (200) accounts per `launch_campaign` task in account id order: each task queues the next chunk behind whatever waits on the mailing worker by then, so booking mail waits for one chunk, never for a whole campaign (`CAPACITY.md`, finding 8). `Campaign.queued_up_to` is the cursor; a task whose cursor is out of date stops (one chain at a time), and `launch_due` resumes a stopped chain from it. `queue_mail` runs every chunk at once, for tests and commands. `cancel` withdraws mail not yet sent. `send_test` sends the mail to its author (`EmailMessage.is_test`, subject "[Test] …", the author's preferences don't apply, blocks do). `stats` gives the results page's numbers. `seed_mailing` seeds three drafts: *Coolest Projects* ("Everyone active": the two activity attributes ORed, with the same `ACTIVE_WITHIN_DAYS` = 365), *CoderDojo Girlz* (families with a girl or a child whose gender isn't listed) and *New dojo opening* (families within 20 km of a new dojo).
- **The organisation dashboard** (`/manage/…`, `campaigns/manage/` and `mailing/manage/`, shell `core/_manage_base.html`, the organisation `admin` role, each page through its area with `accounts.organisation.require_area`, 404 otherwise; reached through the nav's one *Manage* link and `/manage/`, see "One management area" below): *Campaigns* (list with results, create/edit a draft with template variables as `name: value` lines, preview in every language, audience count and sample, send a test, launch, cancel) and *Segments* (list with counts, and a builder: groups about accounts or about "the same child", all/any, nested groups, rules added through fields that fit the attribute via htmx `segment_rule_fields`, each shown as a sentence from `SegmentAttribute.describe`, values read with `value_from_form`; live count and sample) *Journeys* (list, create, preview, test, activate/pause, results and who gets it on the next run), and *Mail templates* (every template with its languages and what uses it; edit one language at a time with a preview on `SAMPLE_CONTEXT` example data, the subject and body checked by `TemplateVersionForm` so a broken template is never saved; a missing language starts from the English text; create campaign templates; delete a language version or a campaign template, never the English fallback, a template the site sends itself (`SYSTEM_TEMPLATE_KEYS`) or one a draft or queued campaign still uses), *Mail queue* (`mailing.manage.mail_queue`, `/manage/mail/`: counts, a warning when due mail has waited over 30 minutes (workers down), mail waiting to be sent, failed mail and `BounceRecord`s of the last 30 days, `EmailSuppression`s, filtered by address; *Send again* per failed mail and *Send all again*, *Unblock* per address, and *Block an address* (`mailing.forms.BlockAddressForm`); *Blocked domains* with *Block a domain* (`BlockDomainForm`): `mailing.BlockedDomain`, every address in a domain and its subdomains, e.g. the seeded demo data's made-up `coderdojo-demo.example`, checked with the address blocks in `mailing.services.is_suppressed_address`, so at queuing, right before sending, on *Send again* and on an email change) and *Mail log* (`mailing.manage.mail_log`, `/manage/mail/log/`: every mail newest first, filtered by address or subject, status and kind, 50 per page, *Send again* on failed rows; never a mail's body). Sending again, blocking and unblocking go only through `mailing/queue_actions.py` (`retry`, `retry_failed`, `block`, `unblock`, `block_domain`, `unblock_domain`; `MailQueueError`): a retry puts the same row back to `pending` (only a `failed` one, not when its content was cleared or its address is blocked) and the worker re-checks consent and blocks before it goes; a block by hand creates an `EmailSuppression` (*Blocked by hand*) and withdraws the address's pending mail (the worker re-checks blocks only for mail to an account); an unblock deletes the `EmailSuppression` with `delete()`; the audit log records who did either, and neither touches the person's preferences. All of them also keep their full Django admin pages, for fixing things by hand. The same shell has a *Public site* group with *Promotions* (`content/manage.py`, see "Organisation-run events" above) and *Sponsors*, a *Volunteers* group for the reviewer role only (*Background checks* and *Applications*, `applications/manage.py`, see "Applications → background check → approval"), an *Accounts* group with *Privacy* (`privacy/views.py`: find an account and download its data for a request by mail or post, see "Privacy"), an *Organisation* group with *People* (the `people` area), *Audit log* (the `audit_log` area, see "Audit log") and *Django admin* (every organisation role; `DATA_MODEL.md` §23, see "Organisation roles"), and a *Ninjas* group with *Awards* (`events/manage.py`, `events.forms.BadgeForm`: create and edit badges; the icon is a standard one from the `awards` image library or an uploaded raster image, deliberately never an SVG upload since it can carry script; an award a ninja already has can't be removed there, only in the Django admin).
- **A dojo's own mail** (`DATA_MODEL.md` §25): a dojo mailing is a `Campaign` with `dojo` set, written and sent by the dojo's champion on the dojo's *Mail* pages (`campaigns/dojo_views.py`, `SEND_MAIL`) and seen (never edited, tested or sent) by the organisation on *Campaigns*. News for its families is `dojo_news` in the `dojo_message` template (a system template) with the dojo's own subject and message inserted as variables (never rendered as a template; `Campaign` is a `TranslatableModel` in the dojo's languages), Reply-To the dojo's email address (`EmailMessage.reply_to`, and the dojo's name in From), at most `MAILING_DOJO_MAILINGS_PER_30_DAYS`, to one of the prepared audiences in `campaigns/dojo_audiences.py` (each a segment definition limited to the dojo, frozen at launch; the ones picking children by their details are child groups, so only with the consent). One audience is the dojo's own team (active champion and mentors): that's `volunteer` mail in the `dojo_team_message` frame, not stopped by a dojo mute and outside the limit; each `Audience` names its `category` and `template`, which the form copies onto the `Campaign`. `campaigns.services` checks and queues it through its dojo branch (`launch_problems`, `audience`, `wanting`, `dojo_context`). The dojo's team sees counts, never families' addresses, also on its own *Mail queue* (`dojo_mail_queue`). The attributes behind the audiences (`campaigns/segmentation/attributes/dojo.py`) are in the registry; `in_builder = False` keeps one without builder fields out of the organisation's segment builder.
- **Consent** (`mailing/preferences.py`): `MailPreference` is an account's choice per category (no row = the default); `ConsentEvent` is the append-only log of every change (who, what, when, source, `PRIVACY_WORDING_VERSION`), written only by `set_preference(user, category, subscribed, source)`. Never write either model directly. `is_subscribed()` answers for one account, `subscribed_q(category)` filters a `User` queryset in the database. `EmailSuppression` blocks an address whatever its preferences (hard bounce, complaint, by hand). On top of the category, an account can **mute one dojo's `dojo_news`** (`DojoMailMute`, `DATA_MODEL.md` §25), only through `set_dojo_mute(user, dojo, muted, source)` (it logs a `ConsentEvent` with the dojo); *Your dojos* on Mail preferences lists the family's dojos (`mailing/dojo_families.py`: a child's home dojo or a visit in the last `MAILING_DOJO_NEWS_ACTIVE_DAYS`, the one definition of a dojo's families, also used by the new-sessions digest) plus any muted one. The approved privacy explanation is one partial, `mailing/partials/_privacy_explanation.html`, shown on the Mail preferences page and next to the newsletter opt-in on family sign-up; change its wording only together with `PRIVACY_WORDING_VERSION`.
- **`send(user, category, template_key, context, idempotency_key=None, campaign=None, send_after=None, address=None, dojo=None)`** (`mailing/services.py`) is the only way to send mail to an account. `dojo` is the dojo a `dojo_news` mail is from: it's stored on the row, a family that muted that dojo doesn't get it (checked again before sending), and its unsubscribe link (and `List-Unsubscribe`) carries the dojo, so the page offers "only this dojo", "every dojo's news" or "all optional mail" (a one-click POST mutes the dojo). Any code that sends a dojo's news passes it. `address` sends `service` mail somewhere other than `user.email` (only the confirmation of a new email address uses it). Someone without an account yet (an organisation invitation) gets `service` mail through `send_to_address(address, template_key, context, language=, name=)`: no `user`, only the address block applies. It renders the template in the account's language right away (the row is the record of exactly what was sent; `recipient_name`, `site_url` and, for opt-out categories, `unsubscribe_url` are added to the context) and inserts an `EmailMessage`: `pending`, or `suppressed` with a `status_reason` (inactive account, category not for this account type, not subscribed, no address, blocked address). An `idempotency_key` makes a repeat call a no-op. It never talks to SMTP and never calls `.delay()`. Links in mail use `settings.SITE_URL` (there's no request in a worker).
- **The database is the mail queue** (`mailing/tasks.py`). `send_pending_emails` (beat, every 10 s, `periodic` queue) only dispatches: it claims pending rows by `priority`, `created_at` with `select_for_update(skip_locked=True)`, never more than `MAILING_CLAIM_LIMIT` in flight, marks them `sending` and hands them out as a `group` of `send_email_batch` subtasks (`MAILING_BATCH_SIZE` each). `send_email_batch` (default queue) sends a chunk over one SMTP connection; Celery does the throttling (`rate_limit=MAILING_BATCH_RATE_LIMIT`) and the retries (`autoretry_for=TransientSendError`, backoff from 30 s up to 10 min, 5 retries; `SendBatchTask.on_failure` fails what's left after the last one). Each row is marked `sent` right after its own send, so a retry never mails anyone twice; a 5xx about one recipient fails only that row. Mail is built as `QueuedEmail`, which allows 998-character header lines: otherwise the email package RFC 2047-encodes the long `List-Unsubscribe` URL and one-click unsubscribe breaks. Opt-out categories get `List-Unsubscribe` and `List-Unsubscribe-Post` (RFC 8058). `requeue_stuck_emails` (beat, every 15 min) puts rows `sending` for more than `MAILING_CLAIM_TIMEOUT_MINUTES` back and logs the queue's state.
- **Pages** (`mailing/urls.py`): `/account/mail/` (`mail_preferences`, login required) has a checkbox per category the account can switch off, a switch per dojo (*Your dojos*, above), a switch per child for the consent above (`accounts.consent.set_consent`) and the mail language, linked from the account page. `/mail/unsubscribe/<token>/` (`mail_unsubscribe`) needs no login: the token is `django.core.signing` of user + category, plus the dojo for a dojo's news (salt `mailing.unsubscribe`, no expiry). GET confirms, POST unsubscribes (one category, or `scope=all`). It's `csrf_exempt` because mail providers' one-click POST carries no CSRF token; the signed token is all it trusts.
- **Bounces** (`mailing/bounce.py`, the `process_bounces` beat task every 5 min, off while `MAILING_BOUNCE_IMAP_HOST` is empty). Every mail's envelope sender is `MAILING_BOUNCE_ADDRESS` (with `{id}` → the row id for VERP when the host takes plus-addressing); the `From` header people see stays `DEFAULT_FROM_EMAIL`. `BounceProcessor` (connect → get_new_messages → parse → handle) reads the bounce mailbox over IMAP (`ImapMailbox`, production) or POP3 (`Pop3Mailbox`, the devcontainer, where Mailpit is the mailbox), chosen by `MAILING_BOUNCE_PROTOCOL`. It parses DSNs (RFC 3464) and complaint reports (ARF), plus plain-text bounces that quote our Message-ID and a status code; auto-replies and anything else are skipped. Matching is by VERP address, else by our `message_id`. Each result is a `BounceRecord`. A hard bounce marks the mail `bounced` and adds an `EmailSuppression`; `MAILING_SOFT_BOUNCE_LIMIT` soft bounces within the window suppress too; a complaint switches off the account's optional categories (ConsentEvent source `bounce`) without blocking account or booking mail. `ProcessedImapMessage` records every handled message per mailbox, so none is handled twice; nothing is ever deleted from the mailbox.
- **Registrations and cancellations:** `Registration.created_at` is when the ninja was signed up. Cancelling (`accounts.views.cancel_registration` → `events.registrations.cancel`, which promotes the child waiting longest only into a place that's really free) still deletes the `Registration`, so places and the waiting list work as before, but first appends an `events.RegistrationCancellation` (ninja, event, whether it was waitlisted, when it was signed up and cancelled, by whom), the log the `cancellations` attribute reads.
- **Engagement snapshot** (`events/engagement.py`, model `events.NinjaEngagement`): how each child comes to sessions, rebuilt every night at 03:00 by `events.tasks.rebuild_engagement` (default queue) and on demand by `manage.py rebuild_engagement` (`start.sh` runs it after seeding). One row per child and dojo they came to in the last year, plus an overall row (`dojo` empty) measured at their main dojo (home dojo, else the one they visited most) that counts visits anywhere. Only sessions meant for the child count as offered (`is_aimed_at`: age range, a girls' session only for girls); "came" is marked present, or a confirmed place at a session where the dojo marked nobody (`from_marked_attendance` records that). Stages, first match wins: aged out, never came, new, lapsed, at risk (`AT_RISK_MISSED` = 3 in a row), regular (`REGULAR_MIN_VISITS` = 3 and `REGULAR_MIN_RATE` = 0.5 in `WINDOW_DAYS` = 180), occasional; the thresholds are constants at the top of the module. The dojo team's attendance rows show the child's stage at that dojo, with the figures as a tooltip (`dojos.views._attendance_context` → `engagement_by_ninja`, looked up with `core`'s `get_item` filter). It's rebuilt wholesale, so an edit in the admin only lasts until the next night.
- **Change over time and journeys** (Tier 3). Each nightly engagement rebuild compares every child's overall stage with the previous night's and appends a `events.NinjaEngagementChange` (from, to, day; not on the very first build, and never twice for one day). The `stage_changed` attribute (`{"from": [...] or [], "to": [...], "days": N}`) reads it, alongside `no_new_belt_within_days` (children) and `not_on_team_within_days` (accounts, via `Event.team`). A **journey** (`campaigns.Journey`, service `campaigns/journeys.py`, dashboard *Journeys*) is a standing campaign: `run()` (beat `run_journeys`, daily 18:00, default queue, after the 03:00 rebuild) sends its mail through `send()` to everyone who matches its segment that day, wants its kind of mail and hasn't had it within `cooldown_days` (checked against `JourneyDelivery`, one row per mail); paired with a `stage_changed` rule it's a triggered mail ("we miss you" the week a child becomes at risk). Journeys start paused; `activate` runs the same checks as a campaign launch (`launch_problems`).
- **Automated mail** (`mailing/automated.py`; every one goes through `send()`). A ninja's mail goes to the family (`family_of`: every guardian, plus the ninja's own login when it has an email). `booking_mail` (from `events.views.event_signup`, in the sign-up's transaction: `registration_confirmed` or `registration_waitlisted`) and `waitlist_promoted_mail` (from `accounts.views.cancel_registration`) are `registration` mail. Two daily beat jobs run on the default queue (their beat entries set `options.queue`, so `CELERY_TASK_ROUTES` leaves them off `periodic`): `send_session_reminders` at 09:00 (`reminder`, sessions `MAILING_REMINDER_DAYS_BEFORE` = 2 days ahead) and `announce_new_sessions` at 17:00 (`dojo_news`, one mail per family and dojo for sessions that opened since the last run; a family belongs to a dojo through a child's home dojo or a visit in the last `MAILING_DOJO_NEWS_ACTIVE_DAYS`). `Event.published_at` is set in `Event.save()` the first time a session opens; `announced_at` is set by the digest. Every automated mail has an idempotency key, so re-running a job queues nothing twice. A missing template is logged and skipped, never an error for the family. The templates reach production through `manage.py load_mail_templates` (create-only, never overwrites), which `deploy.sh` runs after `migrate`; `seed_mailing` calls it too. **Changing the text of a template that already exists** therefore also needs a data migration that updates only the rows still exactly as seeded (a hash of the old subject and body), as `mailing/migrations/0012_login_link_template_updates.py` does; an edited row stays its editor's.
- **Testing mail by hand** (devcontainer): all mail goes to Mailpit, whose UI at `https://coolregistration.localhost/mails/` is where you check it. `manage.py simulate_bounce [id] --kind hard|soft|complaint [--process]` (DEBUG only) sends a realistic bounce report for a sent mail into Mailpit, where `process_bounces` finds it over POP3. Mailpit's chaos mode (`PUT /mails/api/v1/chaos`) makes it refuse mail, to watch retries and failures.
